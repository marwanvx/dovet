# Questions for the owner

When a spec doesn't decide something, the agent answers it itself and records question and answer here, under "Answered" ([build loop](../../workflow/build-loop.md) step 6). The owner never has to answer. To change an answer, add a line `- **Override (owner, <date>):** <what you want instead>` to that entry; the next session applies it and adds an `**Override applied:**` line. "Waiting for the owner" is only for things no agent can do (an account, money, a secret, a physical device).

## Waiting for the owner

### W1 (M0-09): the release signing key
Needed only before the first public release (owner, 2026-10-12: not now); building continues without it, tested with throwaway keys. About 15 minutes, once:
1. **The protected environment.** On github.com open the `dovet` repository > **Settings** > **Environments** > **New environment**, name it `release`, click **Configure environment**. Tick **Required reviewers** and add yourself. Under **Deployment branches and tags** choose **Selected branches and tags** > **Add deployment branch or tag rule** > type **Tag**, pattern `v*`. Click **Save protection rules**.
2. **Make the key.** Install Bun if you don't have it: on macOS or Linux run `curl -fsSL https://bun.sh/install | bash`; on Windows run `powershell -c "irm bun.sh/install.ps1 | iex"` (then open a new terminal). On the repository's GitHub page click **Code** > **Download ZIP**, unzip it, open a terminal in the unzipped folder and run `bun scripts/sign-release.ts --new-key`. It prints a private key and a public key.
3. **Store the private key.** In the `release` environment page from step 1, under **Environment secrets** click **Add environment secret**, name `DOVET_RELEASE_KEY`, paste the private key, **Add secret**. Also keep a copy somewhere safe offline (a password manager). Never paste it anywhere else, including to the agent. Then clear the terminal (`clear`, or Cmd+K on macOS) and close it.
4. **Give the agent the public key.** Paste the public key line into your next message to the agent (it is safe to share). The agent puts it into Dovet (`src/cli/release-signature.ts`); from then on a `v*` tag releases.

### Q3 (M0-07): do snapshots use the user's git objects as an alternate?
- **What's missing:** checkpoints "Private object store" and ADR-19 had snapshots read the user's repository objects through `GIT_ALTERNATE_OBJECT_DIRECTORIES`, so existing blobs would not be copied. In the prototype, a reviewer found that git then "freshens" an already-stored object by updating its modification time, which changes a file inside the user's `.git/objects` (the spec says nothing is written there), and that a checkpoint's tree can then refer to objects that only the user's repository holds, so a user's `git gc --prune=now` or history rewrite could make a rewind fail.
- **Recommended answer:** no alternate. The private store holds every blob itself. A checkpoint can always be restored, and nothing in `.git` changes, not even a timestamp. Cost: the first snapshot stores a compressed copy of the workspace (7.8 MB for 59 MB of source files in the 100,000-file benchmark); `dovet gc` still removes what no retained checkpoint needs.
- **Meanwhile:** built that way, marked `ASSUMPTION (QUESTIONS Q3)` in `src/store/snapshots/snapshotter.ts`. This spec-change PR applies it to checkpoints "Git tree snapshots" and ADR-19. It changes an ADR, so it waits for the owner. If you agree, just write "yes".

### Q4 (M0-07): how are new blobs written to the private store?
- **What's missing:** checkpoints "Snapshot (filter-free)" step 3 named `git hash-object --no-filters -w --stdin-paths`, which writes one loose object file per blob. Measured on GitHub's Windows runner (3,000 new files, C: drive): 23.3 s (7.8 ms per file); the same blobs through `git fast-import` into one pack: 0.28 s. The 100,000-file first snapshot took 13 minutes with `hash-object`. Git's `core.fsync` and compression settings made no difference. Linux is about 10 times faster with the pack too.
- **Recommended answer:** `git fast-import` with exact-length blobs, run in an empty bare repository of Dovet's own so a crash report can't land in the user's `.git` (the git docs say fast-import writes crash reports to the top level of the repository it runs in). Checkpoints step 3 and ADR-19's plumbing list now say so. Same filter safety (fast-import runs none; a test feeds it file content that looks like fast-import commands). This also corrects ADR-19's "(lint rule)" for forbidding `git add`/`checkout`: a test scans the module's source instead.
- **Meanwhile:** built that way in PR #13. This spec-change PR changes ADR-19, so it waits for the owner. If you agree, just write "yes".

### Q5 (M0-07 session): upgrade TypeScript to 7?
- **What's missing:** Dependabot opened PR #12 (`typescript` 6.0.3 → 7.0.2). Nothing in the specs says which version to use; PROGRESS (M0-01) records that it is pinned to 6.0.3 because `dependency-cruiser` needs `<7` (Bun's own `bun check` does the type check and needs no `typescript` package, ADR-1).
- **Findings:** with 7.0.2 the three import-boundary tests (AC-ARCH-04) fail: `dependency-cruiser` stops seeing TypeScript imports and exits cleanly on a forbidden import. Its own source and docs say "support for typescript@>=7 will follow when its API is published and stable"; its newest release (18.6.0) still caps at `<7`. TypeScript 7.0.2's package only exposes `unstable/*` APIs. Moving to 7 therefore means replacing the boundary checker (an ADR-22 change); Bun's import scanner omits type-only imports, so a replacement needs its own scanner for `import type` and `export type … from`.
- **Recommended answer:** stay on 6.0.3 and leave #12 unmerged until `dependency-cruiser` supports 7 or we replace it.
- **Answer (owner, 2026-10-12):** keep 6.0.3 for now, no upgrade; the owner will decide about PR #12. Applied: nothing changed; the agent did not touch #12.

### Q6 (M0-07 session): AC-CKPT-05's 200 ms budget on Windows
- **What's missing:** AC-CKPT-05 says a second snapshot of an unchanged 10,000-file repository takes under 200 ms. M0 measured on CI runners (20,000 files): Linux 190 ms, macOS 157 ms, Windows 498 ms (a repeat snapshot is as fast as `git status` or faster: Windows `git status` took 2.4 s). A Windows `git` process costs about 27 ms to start, and a snapshot starts about six, so Windows has a floor of about 160 ms before touching a file; 10,000 files is about 250 ms.
- **Recommended answer:** keep 200 ms for Linux and macOS and allow 400 ms on Windows, for the 10,000-file case on CI runners. Fewer processes (for example a long-lived `git cat-file`/`update-index` helper) is the fix if real use needs more, and it can wait.
- **Meanwhile:** nothing is built on it yet; the test for AC-CKPT-05 belongs to the M2 snapshot task, which applies the per-OS budget and puts it into the spec in its spec-change PR. If you agree, just write "yes".

### Q7 (M0-06): how strictly is the vendored pi-tui type-checked?
- **What's missing:** AGENTS.md says "TypeScript strict; no `any`", and Dovet's `tsconfig.json` adds three checks on top of `strict` (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`). pi-tui is written for `strict` only: under Dovet's settings its 1.1.0 source has 221 errors in 20 files. Nothing says whether vendored code must meet Dovet's extra checks.
- **Answer:** vendored code is checked with its upstream's settings (`strict`), not Dovet's extras. Patching about 220 lines of someone else's code would turn every re-sync with pi-tui into a merge, and those three checks catch mistakes in code we write, not in a library that already has its own tests. `src/tui/vendor/pi-tui/tsconfig.json` is a separate TypeScript project (a project reference from the root, `bun check -b`), so Dovet's own code keeps every check, including where it calls pi-tui. Dovet's own changes inside the vendored copy are few and marked `Dovet:` (listed in its `VENDORED.md`). Biome already skipped `src/tui/vendor`.

### Q8 (M0-06, owner): Dovet's own background color
- **Owner decision (2026-10-12):** "we must have a background for the TUI itself, not rely on the terminal the user is running from." The spec only said the theme has light and dark variants matched to the terminal.
- **How it's applied:** tui "Rendering rules" now says Dovet paints its own background and default text color (setting only one of them makes text unreadable on some terminals). Choices the agent made: while Dovet runs it sets the terminal's own default colors (OSC 10/11), so the whole window matches, and gives them back on exit (OSC 110/111); the owner's second run showed painting only the drawn lines leaves the empty rows, edges and window padding in the terminal's color. It also paints every line it draws, for terminals that ignore OSC 10/11; detection of the terminal's light/dark still picks the starting variant; no background with `NO_COLOR` or 16-color terminals (no way to choose a matching shade there). The demo in PR #17 shows it, so the owner's terminal run covers it.

### Q9 (M0-06 session, for the record): why the binaries are big
- **Question (owner):** the downloads are large though little is built yet.
- **Answer:** it is the Bun runtime, which every compiled Bun executable carries (ADR-1). Measured on Linux x64 with Bun 1.4.3: a one-line `console.log("hi")` compiles to 86.6 MB, `dovet` to 86.6 MB, `tui-demo` to 87.0 MB; Dovet's own JavaScript, minified, is about 0.3 MB. Windows: 91.9 MB for the one-liner. Compressed downloads are 31–42 MB. Size therefore stays roughly flat as Dovet grows. Shrinking the runtime (UPX-style packers) is not used: it breaks macOS code signatures and sets off antivirus scanners. Revisit only if Bun ships a smaller runtime.

### Q10 (M0-09): M0-09 split in three tasks
- **What's missing:** M0-09 asked for the release workflow, both install scripts and `dovet update` in one task, well over the ~400-line PR limit.
- **Answer:** three tasks in build order: M0-09 signed release archives (notices, `SHA256SUMS`, signature, attestations), M0-10 `dovet update` and rollback (AC-ARCH-02), M0-11 install scripts (AC-CLI-07, which needs `dovet update` for its Windows junction part). The exit check is now M0-12. Every criterion stays in exactly one task.

### Q11 (M0-09): signature format, and how the release workflow is tested before a key exists
- **What's missing:** architecture "Distribution" says `SHA256SUMS` is Ed25519-signed and the public key embedded, but not the file formats, nor how the pipeline is proven without the owner's key.
- **Answer:** `SHA256SUMS` lines are `<sha256 hex>  <file name>` (the `sha256sum` format); the signature is `SHA256SUMS.sig`, the raw 64-byte Ed25519 signature of its exact bytes (what `openssl pkeyutl -verify -rawin` and WebCrypto both take, for the install scripts). Keys are base64: the private key PKCS#8 (the `DOVET_RELEASE_KEY` secret), public keys raw 32 bytes (`RELEASE_PUBLIC_KEYS`, a list so a rotation can trust old and new). `sign-release.ts` refuses a key whose public half isn't embedded, so a release no install could verify is never published. A pull request touching the release files runs the whole workflow with a throwaway key and does not publish; its archives get real attestations, so `gh attestation verify` is proven in CI (AC-ARCH-03). Those attestations name the pull request's ref, not a `v*` tag; so users verify with `--source-ref refs/tags/v<version>` (now in architecture "Distribution"), and the release workflow's own check passes `--source-ref` of the run's ref. Dependabot pull requests skip the test release (read-only token).

Also listed: the Bun runtime (its `LICENSE.md` for the exact Bun version, kept in `scripts/licenses/`; the build fails for a Bun version without one), `@anthropic-ai/sandbox-runtime` (its helpers ship in `libexec/srt/`), ripgrep (its `LICENSE-MIT` from the pinned archive) and the vendored pi-tui. Noted for later: sandbox-runtime's `apply-seccomp` is linked statically with glibc; the notice carries sandbox-runtime's own license only, as upstream ships it.

### Q14 (M0-10): what `dovet update` decides that the spec left open
- **What's missing:** architecture "Distribution" says `dovet update` downloads the latest release and switches an atomic pointer with the old version kept, but not how the latest version is found, what happens when the server offers an older one, where the rollback target is stored, or how many old versions stay.
- **Answer:** the version comes from the signed `SHA256SUMS` itself (no unsigned "latest" API to trust); a release that isn't newer than the installed one is not installed (stops a replayed old release from downgrading); the previous version is a one-line file `previous` in the install directory, rewritten on update and on rollback so a second rollback returns; an update keeps only the new and the previous version (a failed removal is reported, not hidden). Written into architecture "Distribution"; no decision (ADR) changes.
- **Learned while building:** Bun 1.4.2's `Bun.Archive.extract` keeps file modes (the executable bit) and silently skips symbolic-link entries; `update` still refuses a tree that holds a link, in case a later Bun creates them.

### Q15 (M0-11): how the install scripts check an Ed25519 signature
- **What's missing:** architecture "Distribution" has the install scripts verify the signature on `SHA256SUMS`, but a shell and Windows PowerShell have no Ed25519 built in, and the downloaded `dovet` can't vouch for itself.
- **Answer:** POSIX uses OpenSSL 3 (`pkeyutl -verify -rawin`, the format Q11 chose for this); macOS's LibreSSL 3.3 can't, so the script also tries Homebrew's `openssl@3`, proving each candidate on an RFC 8032 test vector first, and otherwise stops and says what to install. PowerShell 5.1 (what `irm | iex` runs on a stock Windows) has no Ed25519, so `install.ps1` carries its own BigInteger implementation of RFC 8032 verification (public data only, no secrets, so timing doesn't matter), exercised in CI by accepting signatures made with WebCrypto and refusing tampered files and untrusted keys (under Windows PowerShell 5.1 itself). The scripts take the release keys from a line in the script (`DOVET_EMBEDDED_KEYS`, `$EmbeddedKeys`; a test keeps them equal to `RELEASE_PUBLIC_KEYS`) and, for tests, from `DOVET_RELEASE_PUBLIC_KEYS`; with no key at all they refuse to install. Also decided: a release names exactly one archive per target (more than one stops the script), reinstalling over an existing install records the version it left in `previous`, the `linux-arm64-musl` install prints the `apk add ripgrep` line when no `rg` is on PATH (architecture "Distribution"), and the Git for Windows question (platforms) is asked only in an interactive console with winget present. Written into cli-config "Install, PATH and uninstall".

### Q17 (M0-14): how CI updates the real built binary without a hole in the shipped one
- **What's missing:** `dovet update` trusts only the embedded release keys and fetches from GitHub, so it can't be pointed at a test release signed with a throwaway key. The install scripts have env test hooks for that; copying them into the binary would let anyone who can set dovet's environment pick which key `dovet update` trusts. Raised in the M0-14 session; the owner picked the build-time option.
- **Answer:** no hook in the shipped binary. A pull request's build job makes the throwaway key, keeps the private half on that runner, compiles the public half and a loopback update URL (`http://127.0.0.1:47231`) into the test binaries only (`define`), signs the release and a "next" release (the same archives under the next patch version) for the targets the CI runners use, and discards the key. The `install` job on Linux, macOS and Windows installs the built archive with `install.sh` / `install.ps1`, runs it, serves the next release on that port, runs `dovet update`, then `--rollback` twice. A tag build embeds nothing extra, and a test checks that a normal build holds neither the URL nor a key. Written into architecture "Distribution".

### Q18 (M1-02): three small gaps in the platform seam
- **What's missing:** (1) interfaces §2b has `Platform.shells()` but no way to find the other programs Dovet spawns itself (`git`, `rg`, `pdftotext`, clipboard tools), though platforms "Executable resolution" says each is resolved once, asynchronously, skipping the project; (2) `DOVET_DATA_DIR` is an override for tests and portable installs, but the cache directory would still go to `~/.cache` and break that isolation; (3) refusing a UNC or device path needs an error the file tools can turn into their own message.
- **Answer:** (1) `Platform` gets `resolve(program): Promise<AbsPath | undefined>`, cached per session, missing cached as missing; `spawn` refuses a program that isn't an absolute path, so nothing reaches `CreateProcess` unresolved. `shells()` and `clipboard` stay out of `createPlatformCore` until their tasks (M1-20, M3) build them. (2) With `DOVET_DATA_DIR` set, the cache is `<DOVET_DATA_DIR>/cache`. (3) `canonicalize` throws `PathRefused` (message names the rule); tools turn it into a `ToolError`. A relative `DOVET_CONFIG_DIR`/`DOVET_DATA_DIR` is a startup error naming the variable. (4) Children are process-group leaders (`detached`) on Linux and macOS only; on Windows `detached` would leave console grandchildren without a console, and `taskkill /T` kills the tree anyway. `canonicalize` also refuses Git Bash paths other than `/c/...` (`/tmp`, `/usr`) until M1-20 knows where Git is installed, and a Windows link chain that reaches a UNC share through another local link is only caught by the post-resolution check (Windows has already touched the share by then); the file-tool and policy tasks (M1-14, M1-23) must keep refusing UNC input before any file access.
- **Meanwhile:** built that way, marked `ASSUMPTION (QUESTIONS Q18)` in `src/platform/core.ts` and `src/platform/dirs.ts`. The spec-change PR (interfaces §2b `Platform`, cli-config "Directories") follows separately, as dev-workflow requires.

### Q20 (M1-03): seven small gaps in settings loading
- **What's missing:** (1) `DOVET_BUDGET` doesn't say which budget it sets; (2) an invalid value in a Claude Code settings file: cli-config says policy keys stop startup, but those files are written for another tool; (3) which Claude Code files are read and where they sit in the precedence order; (4) what "a renamed key" migrates from while no release has renamed anything yet; (5) whether the settings objects can hold a key called `__proto__`; (6) whether a repo's own `compat.claudeCodeSettings: false` may switch off the user's `~/.claude` rules; (7) what a key written twice in one file means.
- **Answer:** (1) `DOVET_BUDGET` is the session limit (`budget.session`), a plain non-negative number of US dollars (`1e2` is 100; `5abc`, `0x10`, `Infinity` stop startup). (2) In Claude Code files only the portable subset is read (`permissions.allow/ask/deny/additionalDirectories/defaultMode`, `sandbox`); unknown keys inside it are dropped silently, and any invalid value is dropped with a warning that names file, line and key instead of stopping startup, because a value Claude Code accepts and Dovet doesn't (for example `defaultMode: "delegate"`) must not stop someone who is switching from starting Dovet. (3) Lowest to highest: defaults, `~/.claude/settings.json`, user, `.claude/settings.json`, project, `.claude/settings.local.json`, local, env, flags; so each Claude Code file sits just below the Dovet file of the same scope. (4) `src/store/config/migrate.ts` has the mechanism and an empty `MIGRATIONS` list; the tests pass their own steps (the `ui.fullscreen` example of cli-config). The first release that renames a key adds the step. (5) `__proto__` is kept as plain data and reported as an unknown key. (6) No: `compat.claudeCodeSettings: false` in a project or local file turns off only that repo's `.claude/` files; `~/.claude/settings.json` follows only user settings, the environment and flags (a cloned repo must not be able to drop the user's deny rules). (7) The later value wins, as in `JSON.parse`, and the repeat is reported (a startup error in a policy section, a warning elsewhere), so a repeated `permissions` block can't hide deny rules. In a Claude Code file, one invalid list entry is dropped alone with a warning; a Claude Code file that has a syntax error is skipped with a warning (Claude Code reports the same file itself).
- **Meanwhile:** built that way; `ASSUMPTION (QUESTIONS Q20)` is in `src/store/config/env.ts`. The spec-change PR (cli-config "Config files and precedence") follows separately.

On macOS and Windows every keychain error is shown, and a denied or cancelled prompt is shown on every OS: a key never silently lands in a file. Reading checks the keychain first, then the file. (3) An error naming the setting and the missing variable or entry, never a fall-through to the next source: the user asked for that source. (4) Entry `<name>` of service `dovet`, the same place `dovet auth login` stores `<provider>`. (5) Neither: it shows "cmd: command (user settings)", since a command line can contain a secret. (6) `.dovet/settings.json` and `.dovet/settings.local.json`; both live in the repository folder. A `cmd:` there stops startup like any invalid policy key. (7) Unset, as with the `DOVET_*` overrides. (8) Not decided here: the resolver takes the runner as a dependency, and the task that first resolves a key for a real request wires it (`/bin/sh -c` on macOS and Linux, PowerShell on Windows, following the shell rules of the Bash tool).
- **Meanwhile:** built that way; `ASSUMPTION (QUESTIONS Q21)` is in `src/ai/providers/auth.ts`. The spec-change PR (cli-config "Secrets") follows separately.

### Q22 (M1-05): five small gaps in the event log
- **What's missing:** (1) the zod schema of each event type's `data`; (2) which env vars count as secrets for AC-LOG-06, and what replaces them; (3) which paths the startup permission check looks at; (4) what the `.meta.json` sidecar holds and how "stale" is detected; (5) whether a known event type whose `core` flag disagrees with the table is acceptable; (6) how a writer reopening a log that ends in a torn line keeps it readable without rewriting it; (7) what happens to event data that merely looks like a blob reference; (8) who checks invalid state transitions (a `tool.result` without its `tool.call`).
- **Answer:** (1) Each event's data schema is added by the task that first writes that event; until then the envelope is validated and `data` is any JSON. The event types and their core/optional class are in `src/schema/events.ts`. (2) Env vars whose names contain KEY, TOKEN, SECRET, PASSWORD, PASSWD, PASSPHRASE, CREDENTIAL or AUTH, with values of 8 or more characters, plus every resolved credential; each occurrence in any string of an event becomes `[redacted]`, and a `Secret` object is written as `[redacted]`. ### Q28 (M1-09): eight small gaps in the retry policy

### Q35 (M1-16): gaps in Edit
- **What's missing:** (1) how the L2 "file's indent unit" is known when the file uses tabs and `old_string` uses spaces; (2) what staleness allows beyond L0; (3) the read requirement before M1-23; (4) mixed line endings; (5) `file.change.match` has no field in `ToolOutput`; (6) the `quirks.doubleEscapedEdits` unescape needs a model quirk that `ToolContext` doesn't carry; (7) the encoding guess.
- **Answer:** (1) A tab counts as 4, 2 or 8 spaces; L2 tries each and counts the union of distinct match positions (more than one place = the multiple-matches error), so a space-indented `old_string` finds a tab-indented place without guessing the unit. The offset must be equal on every non-blank line; blank lines must be blank on both sides. New lines are re-indented by that offset in the file's indent characters (tabs if more lines start with a tab than a space). Lines the model left unchanged (line diff of `old_string` against `new_string`) keep the file's original bytes. (2) A stale file (hash differs) applies only an exact (L0) unique match; L1/L2, `replace_all` with several matches and "not found" all give the "Read it again" error. (3) As Write (Q34): an unread or partly read file is refused until M1-23 adds the silent read. (4) A file with both CRLF and LF is written with its dominant ending and the result says so. (5) `meta.fileChanges[].match` (`exact|prefix-strip|indent`) was added; the loop copies it into `file.change`. (6) Not built: the unescape needs the model's quirk flags; M1-25 passes them into `ToolContext` (or the loop does the retry) and adds the test. (7) The guess is Windows-1252 when bytes 0x80–0x9F occur, else Latin-1. The closest-match search compares windows of the same line count around lines that share trimmed text with `old_string`, at most 500 windows, threshold 0.9 character similarity.
- **Built:** `src/tools/edit.ts`, `edit-match.ts`, `codec.ts` (decode/encode moved out of `write.ts`). Spec-change PR still to do: tools §3 (items 1, 2, 4, 5, 7).

### Q38 (M1-19): gaps in Bash process lifecycle and output
- **What's missing:** (1) memory: §5.5 streams output to a working file killed at 1 GB, but the tool keeps the output in memory to sanitize it; (2) when the working file exists; (3) how Bash lists changed files with no snapshot service in `ToolContext`; (4) what "their read-state is invalidated" means when a Write to an unread file would read it silently; (5) how the interactive, benign-exit-1 and file-view shapes are recognized before the policy's parser is wired (M1-22); (6) what `Platform` offers for the sweep.
- **Answer:** (1) The cap is 64 MB (`createBashTool({ outputCapBytes })`); past it the command is stopped and the result says `Output exceeded 64 MB; the command was stopped.` A real 1 GB limit needs a streaming sanitizer; ASSUMPTION (QUESTIONS Q38). (2) The file `<session dir>/<id>.txt` is written only when sanitized output passes 30,000 characters (`limitOutput`: 2,000-char preview plus the path); an `ENOSPC`/`EDQUOT` gives `Disk full: output was cut at N bytes` and removes the partial file. (3) `ToolContext.snapshots?: Pick<Snapshotter, "root" | "snapshot" | "changes">` (new `Snapshotter.root` and `changes(before, after)`: name-status plus numstat of `git diff-tree`); M1-25 wires it. A command that is a recognized file view skips the snapshots; the policy's read-only analysis (M1-22) will skip more. (4) Read-state entries are kept, so the changed hash makes the next Write stale ("changed since you read it") and Edit's relaxed rule applies; deleting them would let Write read the file silently and overwrite the change. A changed path with an entry is marked `re-read before editing`. (5) `src/tools/shell-words.ts` is a conservative reader (quotes, operators, redirects; gives up on `$(`, heredocs, subshells, braces) and `shell-command.ts` applies the rules: interactive = editors, pagers, `top`/`htop` without `-b`, `ssh` without a command, `git commit` without a message flag, `git rebase -i`, `git add -p`; benign exit 1 = the last command is grep/rg/egrep/fgrep/find/diff/test/[ or `git diff`/`git grep`; a view = one of the listed programs, one file, no flags that take values, no globs or expansions. M1-22 may replace it with tree-sitter. (6) `Platform.sweep(group, marker)` lists processes (Linux `/proc/<pid>/{stat,cmdline,environ}`, macOS `ps` and `ps eww`), picks members of the group and `DOVET_RUN=<uuid>` carriers, SIGTERM then SIGKILL after the grace period, and returns their names (at most three shown); it runs right after the shell exits, before the 500 ms pipe drain, so a backgrounded child holding stdout doesn't delay the result. Windows returns nothing (`taskkill /T`). (7) The working file holds the sanitized text as printed (no JSON pretty-printing or re-wrapping, unlike the other tools' offload); timeout and interrupt results show the same head-and-tail excerpt as failures (10,000 chars). (8) If the sweep itself fails (`ps` missing), the result says so and the group is still killed by `killTree`. (9) The Windows halves of AC-TOOLS-08 and AC-PLAT-04 are not tested here (Git Bash arrives in M1-20); M1-20's "Done when" now lifts those skips. Spec-change PR still to do: tools §5 (items 1–5, 7).
- **Built:** `src/tools/bash.ts` (extended), `shell-words.ts`, `shell-command.ts`, `src/platform/sweep.ts`.
