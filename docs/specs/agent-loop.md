## Turn state machine

```
         submit(input)
 IDLE ─────────────────► PREPARE ──► REQUEST ──► STREAM ──┬─► (no tool calls) ──► FINALIZE ──► IDLE
   ▲                        ▲                             │
   │                        │                             └─► TOOLS ──► (results appended) ──┘ back to PREPARE
   │                        │
   └──── interrupt() from any state except IDLE ──► INTERRUPTING ──► FINALIZE
```

| State | What happens | Exits |
|---|---|---|
| **PREPARE** | (1) budget pre-check ([receipts-budgets](receipts-budgets.md)); (2) loop detector check; (3) compaction check ([context](context.md)); (4) the transcript builder renders the request | REQUEST, or FINALIZE if a budget or loop guard stops the turn |
| **REQUEST** | `model.request` event; open the stream with the turn's `AbortSignal` | STREAM, or retry per [providers §7](providers.md) |
| **STREAM** | Forward deltas to the UI as transient events; accumulate; on completion persist `model.response` | Handled by stop reason (table below) |
| **TOOLS** | Validate → policy → execute → persist results ([tools](tools.md), [permissions](permissions.md)) | PREPARE (next model request) |
| **FINALIZE** | Build and persist the receipt; `turn.end`; flush and fsync the log; update the session metadata sidecar | IDLE |

## Stop-reason handling

| Normalized stop reason | Action |
|---|---|
| `end_turn` | FINALIZE. |
| `tool_use` | TOOLS. |
| `max_tokens` with a tool call in the response | **Do not run any tool from this response** (a truncated input can still pass validation). Append a user message: `Your previous response was cut off at the output limit while writing a tool call. Retry with a smaller step.` Back to PREPARE. Counts toward the loop detector. |
| `max_tokens` without a tool call | FINALIZE; the receipt notes "response truncated at output limit". |
| `context_exceeded` | Trigger compaction ([context](context.md)), then retry the same request in the new epoch (once). If it fails again: FINALIZE with error. |
| `refusal` | Never run that turn's tools. Show the refusal category and explanation. FINALIZE with reason `refusal`. (If server-side fallback is enabled and a fallback model answered, the response arrives as normal and the receipt records both models.) |
| `pause` (Anthropic `pause_turn`) | Re-send the transcript with the paused assistant turn appended, without adding a user message. Max 5 continuations per turn, then FINALIZE with a warning. |
| `stop_sequence` / `other` | FINALIZE; log the raw reason. |
| **Empty or thinking-only response** (no text, no tool call) | Not appended. Retry once; if it happens again, FINALIZE with `The model returned no answer.` |
| `refusal` **before any visible output** (output filter stopped the reply during thinking) | Retry once **only** if the category is not one Anthropic bills before output (`cyber`, `general_harms`), since those have measurable false positives. Billed categories (`bio`, `frontier_llm`, `reasoning_extraction`) are handled as `refusal` at once: a retry would cost money and refuse again. |

**Every `tool_use` must get exactly one `tool_result`** in the next user message, in the same order the model emitted them. This invariant is asserted before each request; a violation is an `InvariantViolation` (a bug).

## Early execution of read-only tools

Waiting for the whole response before running anything wastes the time the model spends writing later tool calls. The Anthropic SDK's own tool runner has a `runToolsEagerly` option for this reason [VERIFIED 2026-10-11]. Dovet does the same, safely:
- As soon as a tool-call block **completes** during streaming (Anthropic `content_block_stop`; Responses `response.output_item.done`; Interactions step done), if the tool is a **local read** (Read, Grep, Glob: parallel-safe, no network) **and** the policy decides `allow` without a prompt, start it immediately.
- Never start early: mutating tools, shell commands, WebFetch (network), or anything that needs a prompt. These wait for the complete response and the stop-reason check.
- If the response ends with `refusal`, `max_tokens` + tool call, or an interrupt: early results are **discarded** (not sent). Reads have no side effects, so this is safe.
- Results are still returned in emitted order, in one message.

**Decided while building (QUESTIONS Q46):** early execution is Read, Grep and Glob only, and only when the decision is `allow` without a prompt. Early results are discarded on a refusal, on `max_tokens` with a tool call, or on an interrupt, and are returned in emitted order otherwise.

## Tool execution within a turn

1. Parse and validate all tool calls from the response (zod). Invalid → `is_error` result with `INVALID_JSON` or a schema error message naming the field. Tool-input JSON is parsed **strictly**: no lenient repair that could reinterpret escapes. (Lenient repair can turn `C:\Users\unicorn` into CJK characters by reading `\u` as a Unicode escape.)
2. Partition in emitted order: consecutive **parallel-safe** calls form a batch (run concurrently, max 8); each **mutating** call runs alone, in order.
3. Before each call: policy evaluation ([permissions](permissions.md)). If it needs the user, emit `permission.request` and wait. **Prompts are shown one at a time, in emitted order**, even for calls in a parallel batch (calls not needing a prompt proceed meanwhile). After each answer, the remaining pending calls are **re-evaluated**, so a "don't ask again" covers identical calls in the same batch instead of prompting twice. A call naming an unknown tool gets `is_error` `Unknown tool <name>.` without blocking the batch. Waiting does not time out in interactive mode; in headless mode (`dontAsk` semantics) it resolves as deny immediately. Per [permissions §6](permissions.md), a "No" without a comment **stops the turn**: remaining calls get `is_error` results "Not run: the user stopped this turn" and the loop goes to FINALIZE. Dismissing a question dialog with Esc ([tools §4.3](tools.md)) stops the turn the same way.
4. Execute with the turn's `AbortSignal` and the tool's timeout.
5. Persist `tool.result` (and `file.change` events) as each finishes; the UI updates live. **No failure cascade:** every call returns its own result; a failing call (any tool, including a failing shell command) never cancels its siblings. Only a user's "No" (step 3) or an interrupt stops the remaining calls. The model sees each failure and decides what to re-run.
5b. **Request-size guard (append-only safety):** before a tool result or attachment is appended, the builder computes the next request's body size. If it would exceed 90% of the provider's request cap (Anthropic 32 MB; lower on Bedrock/Vertex), the result is replaced by an `is_error` result naming the size and suggesting a smaller read or `/compact`. Once appended, an over-cap item could never be removed, and every later request would fail.
6. Results are appended as **one** user message containing all `tool_result` parts, in emitted order (splitting them across messages trains the model to stop making parallel calls [VERIFIED 2026-10-10]).

**Decided while building (QUESTIONS Q46):**
- Result size cap: 32 MB by default, 16 MB for providers that document a lower request limit. Over 90% of it, the result is replaced by an `is_error` naming the byte size and suggesting a smaller read or `/compact`.
- A prompt answered "No" without a comment, or dismissed with Esc, stops the turn: the remaining calls get "Not run: the user stopped this turn". "No" with a comment denies only that call. Headless (`dontAsk`) denies at once.
- A user interrupt writes `Interrupted by the user before this tool finished.` results so the transcript stays valid; SIGTERM/SIGHUP write none (crash recovery on resume completes them).

## Interrupts (Esc in the TUI, SIGINT in headless)

| Interrupted during | Behavior |
|---|---|
| PREPARE / REQUEST, **before any model output** | Abort. The turn ends as `cancelled`: its user message is **excluded from the transcript** by that `turn.end` reason (the log keeps it; nothing is rewritten) and is **put back into the input box** for editing, with its attachments. An interrupt at the very first instant of a turn must be honored. |
| STREAM | Abort the stream; the adapter ends with an `aborted` event carrying the completed blocks ([interfaces §3](interfaces.md)). **Keep the work done so far:** every content block that **completed** before the abort (text blocks, thinking blocks whose signature arrived, complete tool-call blocks) is appended as the assistant turn; the one block still in progress is dropped. Complete tool calls in that turn get `is_error` results `Not run: the user interrupted.` A partially streamed text block is kept in the UI (greyed) but not sent. The next user message starts with the instruction part `The user interrupted your response. Blocks that finished are kept above; the rest was discarded.` If no block completed, **or only thinking/reasoning blocks completed** (an assistant turn with no text or tool call may be rejected), nothing is appended. Per-protocol validity of kept partial turns is covered by the interrupt integration tests. |
| TOOLS | Running tools get the abort signal (processes are killed as a tree, [platforms](platforms.md)). Every pending and running call gets a `tool_result` with `is_error: true`, content `Interrupted by the user before this tool finished.` (completed calls keep their real results). These results are appended so the transcript stays valid. |
| Waiting on a permission prompt | The prompt closes as "deny (interrupted)". Same as TOOLS. |

A second Esc within 1 s of an interrupt does nothing more (no double handling). Ctrl+C twice within 1 s exits ([tui](tui.md)).

**Queued input:** the user may type and submit while a turn runs. Messages are queued (shown as "queued (N)"; editable with ↑ until sent). At the next request boundary, all queued messages are delivered together: as text parts **after the `tool_result` parts in the same user message** when a tool round just completed, otherwise as the next user message. `Ctrl+Enter` is the one explicit exception: it sends the queue immediately, interrupting the current request and keeping its completed blocks.
- **Esc interrupts and moves queued messages back into the input box**, so the user decides what to send after stopping the agent. They are never auto-sent after an interrupt. ↑ pulls queued messages back for editing while the turn runs, without interrupting.
- **Queued messages are never lost:** if the turn ends for any reason (guard, budget, error, refusal, max requests), they move back into the input box (interactive) or are delivered as the next turn (headless). Their attachments and `@` mentions travel with them.
- If the model ends its turn (`end_turn`) while messages are queued, the next turn starts immediately with them, so steering is never ignored while the model wraps up.
- Without Ctrl+Enter, a queued message never interrupts a running request (incl. extended thinking).

**Decided while building (QUESTIONS Q47):**
- A queued message is `{ text, attachments: (ImagePart | DocumentPart)[] }`: files travel as blob refs, `@` mentions as text.
- The pairing invariant (every `tool_use` gets exactly one `tool_result`, in order) is proven by rendering the interrupted transcript through the real adapter; each provider package re-proves it for its protocols.
- A whitespace-only text block counts as nothing completed, so thinking-only or empty completions append nothing.

## Harness messages during a turn

All are **appended** turn-scoped system messages (never inserted and later deleted, so the cache and preserved thinking stay valid), delivered per [context §4](context.md), and **never in the same content block as the user's words**. Mid-task user messages go as the user's text after the last `tool_result`. Per-step harness text after tool results makes current models suspect prompt injection and ignore real user messages, so Dovet adds **no per-step countdowns or reminders**, only these occasional ones:

| Message | When | Limit |
|---|---|---|
| `silence-reminder` ("The user hasn't heard from you in a while — say in a few words what you're doing, then continue.") | 5 consecutive tool-calling steps that gave the user nothing to read (no text, no progress-update text) | At most 2 per turn |
| `open-tasks` | **Headless only:** the turn ended with text while the task list still has open items and no blocker was stated | At most 2 automatic continuations per task, then the run ends with the open items listed (exit code 0 with `incomplete: true` in the JSON output) |

A text-only end of turn in an **interactive** session is the end of the turn; the user decides what's next.

## Stream liveness and timeouts

- **No total request timeout** for streaming requests: long reasoning turns legitimately run for many minutes (Anthropic notes Fable-class turns can take minutes).
- **Idle timeout:** if no bytes (any SSE event, including Anthropic `ping` events and keep-alive comments) arrive for **180 s** (`network.streamIdleTimeoutMs`), abort and treat as a retryable network error ([providers §7](providers.md)). The status line shows "waiting for model… 45s" after 15 s of silence so the user knows it's alive.
- **Connect timeout:** 30 s for the TCP/TLS connection; **first byte:** 180 s for the response to start (`network.connectTimeoutMs` covers the first; the idle timeout covers the second). A request that never starts is retried, not waited on silently.
- A stream that dies after completed blocks: handled per [providers §7](providers.md) (completed text/tool-call blocks are kept and the turn continues; otherwise retry).

## Process signals and crashes

| Event | Behavior |
|---|---|
| SIGINT (headless) | Same as interrupt; second SIGINT within 1 s exits with code 130 after flushing the log |
| SIGTERM / SIGHUP (terminal closed) | Kill child process trees, flush + fsync the log, release the session lock, exit 143 / 129. **No synthetic results are written**: unfinished calls are completed by resume's crash recovery ([event-log](event-log.md)), the single code path for every abnormal exit. Their wording says Dovet stopped, never that the user rejected them. |
| SIGTSTP (Ctrl+Z, POSIX) | Restore the terminal (leave raw mode, show cursor, leave alt screen), then stop; on SIGCONT re-enter raw mode and redraw. Running tools keep running |
| Uncaught exception / unhandled rejection | Restore the terminal first, write a crash report (stack, versions, last 50 events' types, no content) to `<data>/crash/`, flush the log, print the report path, exit 70 |
| Windows console close / Ctrl+Break | Same as SIGTERM (`process.on("SIGBREAK")` / console close handler) |

**Decided while building (QUESTIONS Q47):** the agent exposes pure plans (`shutdownPlan`, `exitCodeForSignal`, `sigintOutcome`); only `cli/main.ts` wires `process.on`/`process.exit`. A crash report is `<data>/crash/crash-<ISO stamp>.json`. SIGTSTP leaves tools running; only the terminal is restored.

**Decided while building (QUESTIONS Q62, Q64):**
- Headless installs signal handlers in the CLI composition root (`src/cli/signals.ts`, given an injected runtime). SIGTERM, SIGHUP and SIGBREAK: flush, fsync and release the log; abort; await `killTrees()` (every live group, through the SIGTERM→SIGKILL escalation; concurrent calls share it); then exit 143 or 129. A failed flush prints `dovet: could not flush the session log: …` and a failed kill `dovet: could not kill the running commands: …`; both still exit. No synthetic results are written: crash recovery on resume completes them.
- SIGINT: the first press aborts and warns "press Ctrl+C again within 1 s" without exiting (the turn ends interrupted and exits 130); a second press within the window flushes, aborts and exits 130. A signal before a session attaches aborts and exits without the flush.
- A crash (`uncaughtException`/`unhandledRejection`) writes the report (stack, versions, the last 50 event types only) under `<data>/crash/`, flushes, prints the path and exits 70; it kills nothing.
- When an interrupt keeps completed blocks, the interrupt note is logged so a resume's next request carries it. Interrupted tools all use one wording, `INTERRUPTED_TOOL_TEXT`.

## Loop and runaway protection

| Guard | Default | When triggered |
|---|---|---|
| Max model requests per user turn | 150 | Pause and ask: "The agent has made 150 requests this turn (cost $X). Continue?" |
| Identical failing call | Same tool + same normalized input failing 3 times consecutively | Pause and ask; the message names the call and the error. |
| No-progress detector | 25 consecutive requests with no file change, no new file read, and no new command | Pause and ask. |
| Malformed rounds | 3 consecutive requests in which **every** tool call was invalid JSON, failed schema validation or was cut off by `max_tokens`, in any mix | Pause and ask: "`<model>` sent broken tool calls 3 times in a row (last error: `<error>`). This model may not handle tool calls reliably; try a larger model with `/model`. Continue?" When all three were cut off by `max_tokens`, the hint names the output limit instead of the model. Headless: the turn ends with the same text (exit code 3). |
| Doomed repeat | A request body byte-identical to one that just got a **non-retryable** error | Never sent; the turn ends with the error. |
| Compaction thrash | Context back at the threshold right after 3 compactions in a row | Stop with an actionable error ([context](context.md)) instead of compacting again. |
| Budget | See [receipts-budgets](receipts-budgets.md) | Pause before the next request. |

"Pause and ask" ends the request cycle in a resumable state: the user can say continue (the guard counter resets) or give new instructions. In headless mode a guard ends the run with exit code 3 and a JSON reason.

**Decided while building (QUESTIONS Q46):** identical calls are the same tool with the same normalized input JSON; three consecutive failures pause. Progress is a file change, a new file read or a new command per request; 25 requests without any pause the turn. When all three malformed rounds were cut off by `max_tokens`, the hint names the output limit ("Every call was cut off by the output limit; raise the limit or ask for smaller steps").

## Determinism contract of the transcript builder

[DECISION-3] `buildRequest(sessionState, epoch) → ProviderRequest` is a **pure function** of the events in the epoch plus the frozen epoch header (system prompt, tool definitions, model, params). Tests:

- Same events → byte-identical request body (hash compared).
- Appending events only appends to the request body (prefix property, [providers](providers.md) acceptance criteria).
- No wall-clock, randomness or environment reads inside the builder (lint rule: `agent/transcript/**` may not import `Date`, `crypto.random*` or `process.env`).
- Turns that ended `cancelled` contribute nothing to the transcript (applied identically on every render and replay).

**Decided while building (QUESTIONS Q31):**
- `buildRequest(events, epoch)` returns the adapter's `RenderInput`; `adapter.render` gives the call and the transport the bytes, whose sha256 `model.request` stores. AC-LOG-02 rebuilds each request from the log and compares that hash.
- Results and injected instructions after a model response form one user message, results in call order; a `model.request`, `model.response` or `user.message` closes the group, so a request already sent is never modified. Tool result text goes through `escapeReservedMarkers`; delivery of instructions is the adapter's decision, so the event's `delivery` field is ignored here.
- Event data: `user.message {text}`, `tool.result {callId, status, output}`, `turn.end {reason}`, `model.request {provider, model, params, messageCount, bodySha256, fingerprint}` (`src/schema/event-data.ts`); `model.response` holds the `StoredResponse`.
- Cache monitor: warn when a request reads under half the previous request's cache-read tokens. No warning when the provider reports no cache field, when the previous request read nothing, up to turn 3, or when the miss is expected (effort or thinking change, new epoch, or the previous request older than the cache TTL). `cacheWarning` returns `{text, invariant}`: the loop shows the text and logs the invariant.
- The determinism lint rule (`scripts/lint/no-nondeterminism.grit`) covers `build.ts` and `fingerprint.ts`; the system prompt takes the session date as a clock value from the caller.

## Acceptance criteria

- [ ] **AC-LOOP-01** For every stop reason, a recorded-stream test drives the loop and asserts the next action exactly as in the table.
- [ ] **AC-LOOP-02** Interrupting during each state leaves a transcript that the provider accepts on the next request (integration test per protocol).
- [ ] **AC-LOOP-03** 3 parallel Reads + 1 Edit + 2 Greps emitted in that order: the 3 Reads run concurrently, then the Edit, then the 2 Greps concurrently; results come back in emitted order in one message.
- [ ] **AC-LOOP-04** A truncated tool call at `max_tokens` is never executed.
- [ ] **AC-LOOP-05** A queued user message is delivered after the current tool round without breaking `tool_use`/`tool_result` pairing.
- [ ] **AC-LOOP-06** Each loop guard triggers in a scripted scenario and resumes correctly on "continue".
- [ ] **AC-LOOP-07** Interrupt mid-stream after a complete text block and a complete tool call: both kept; the tool call answered "Not run: the user interrupted"; next request accepted by each protocol.
- [ ] **AC-LOOP-08** A stream silent for 180 s is aborted and retried; Anthropic `ping` events keep a long thinking stream alive.
- [ ] **AC-LOOP-09** SIGTERM during a running tool: child tree killed, log flushed and fsynced, lock released, exit 143.
- [ ] **AC-LOOP-10** Ctrl+Z / `fg` restores raw mode and redraws; an uncaught exception restores the terminal and writes a crash report without message content.
- [ ] **AC-LOOP-11** Two queued messages are delivered together after the tool round, after the `tool_result` parts.
- [ ] **AC-LOOP-12** A batch where a Bash call fails runs every other call and returns all results; two identical calls needing approval prompt once when the first is answered "don't ask again".
- [ ] **AC-LOOP-13** Esc before any output: the turn ends `cancelled`, the prompt and its image return to the input box, and the next request doesn't contain it; Esc with 2 queued messages moves them into the input box unsent; a turn stopped by the request guard keeps its queued messages.
- [ ] **AC-LOOP-14** Guards: 3 rounds of malformed/truncated tool calls pause the turn; a non-retryable error is never followed by a byte-identical request; SIGTERM writes no synthetic results and resume completes them as interrupted.
