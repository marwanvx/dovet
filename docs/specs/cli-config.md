## Commands

| Command | Purpose |
|---|---|
| `dovet` | Interactive session in the current directory |
| `dovet "<prompt>"` | Interactive session starting with that prompt |
| `dovet -p "<prompt>"` | Headless ([tui](tui.md)) |
| `dovet --continue` / `-c` | Resume the most recent session in this project |
| `dovet --resume [id]` / `-r` | Resume a session (picker if no id) |
| `dovet bug` | Prepare a bug report: builds the same redacted bundle as `doctor --report` (versions, OS, settings with secrets removed, doctor results, last crash report; never code, prompts or transcripts), **shows it in full**, then offers: (1) open a pre-filled GitHub issue in the browser, or (2) save the bundle and open an email draft to the project's report address, for users without a GitHub account. Nothing is sent automatically |
| `dovet doctor [--report]` | Diagnostics (`--report` writes a redacted bundle for bug reports: versions, OS, settings with secrets removed, doctor results, last crash report; no session content): versions, shell detection, sandbox dependencies, ripgrep, terminal capabilities, config validation, API key presence per provider (never prints keys), network reachability of configured providers |
| `dovet models [--provider p]` | List models from the catalog with prices and limits |
| `dovet config get/set/edit/path` | Read or write config; `edit` opens `$EDITOR` |
| `dovet sandbox install` / `uninstall` / `status` | Windows one-time sandbox setup (elevated); status everywhere |
| `dovet cost [--since 7d\|30d\|<date>] [--by day\|project\|model\|purpose] [--csv]` | Spending history across all sessions, from local logs only (sidecars and daily ledgers): totals, tokens, cache hit ratio and plan-billed token counts, grouped as asked. |
| `dovet gc` | Blob/session garbage collection |
| `dovet project purge [path] [--dry-run]` | Delete all Dovet state for one project: sessions, blobs only it references, snapshots, its trust entry |
| `dovet auth login [provider] [--device]` / `logout [provider]` / `status` / `export <provider>` / `import <provider>` | Connect, disconnect and list providers (same flow as `/login`); `export`/`import` move an OAuth sign-in to a machine without a browser over a secure channel (the importing machine keeps its own host ID) |
| `dovet sessions rebuild-meta` | Rebuild session metadata sidecars from the logs |
| `dovet update` | Download and install the latest release (versioned directory, atomic switch, previous version kept for `dovet update --rollback`) |
| `dovet sessions list` / `delete <id>` / `delete --older-than <days>` / `delete --larger-than <size>` | Manage stored sessions (logs, blobs, snapshots); `list --size` sorts by disk use |
| `dovet uninstall [--purge]` | Remove Dovet (see below) |
| `dovet --version`, `dovet --help` | — |
| `dovet --explain-defaults` | Prints every default setting with its value and the version it last changed in (glass-box) |

**Global flags:** `--offline` (no catalog refresh, no update check, WebFetch/WebSearch refused; only model requests leave the machine; see "Data and privacy"), `--model`, `--provider`, `--effort`, `--permission-mode <mode>`, `--dangerously-skip-permissions` (= `bypassPermissions`), `--budget`, `--add-dir <path>` (repeatable), `--allowedTools <rule>`, `--disallowedTools <rule>` (repeatable; same flag names as Claude Code, so scripts carry over), `--settings <file|json>`, `--fullscreen`, `--config <path>`, `--debug` (writes request bodies, redacted, and verbose logs).

## Config files and precedence

Highest wins:
1. CLI flags
2. Environment variables (`DOVET_MODEL`, `DOVET_PROVIDER`, `DOVET_EFFORT`, `DOVET_BUDGET`, …)
3. `<workspace>/.dovet/settings.local.json` (personal; Dovet adds it to `.git/info/exclude` on creation, not to `.gitignore`)
4. `<workspace>/.dovet/settings.json` (shared, committed)
5. `<config>/settings.json` (user)
6. Built-in defaults

CLI flags are **session overrides**: no settings write or reload during the session replaces them.

**Coming from Claude Code (zero-cost switching, principle 4):**
- **Read natively, live, with no import step:**
  - instruction files: `CLAUDE.md`, `.claude/rules/` ([context §3](context.md));
  - the **portable subset** of Claude Code settings: `permissions.allow`/`ask`/`deny`/`additionalDirectories`/`defaultMode` and `sandbox` from `~/.claude/settings.json`, `.claude/settings.json` and `.claude/settings.local.json`. These are merged **below** the matching Dovet file of the same scope, are subject to the same trust rules, and are labeled with their source in `/permissions`. Turn this off with `compat.claudeCodeSettings: false`.
  - (v0.2) `.mcp.json`, `.claude/skills/`, `.claude/commands/`, `.claude/agents/`.
- **Not read:** Claude Code's model, hooks (until v0.2), `env`, `apiKeyHelper`, statusline, plugins, managed settings and stored credentials (Claude Code's login tokens are never read or reused).
- **"Don't ask again" writes go to Dovet's own file** (`.dovet/settings.local.json`), never into Claude Code's files.
- The first run in a project with Claude Code settings says what was picked up ("Using 14 permission rules from .claude/settings.json"); there's nothing to import.

Merging: objects deep-merge; arrays of **rules** concatenate across sources (with the precedence semantics of [permissions](permissions.md)); other arrays are replaced by the higher source.

**Security exception:** project config (`.dovet/settings.json` from a cloned repo) is **untrusted** until the user trusts the folder. On the first run in a folder, Dovet shows "This project has Dovet settings (N allow rules, hooks: none). Trust this folder?" Full trust semantics follow [permissions §11](permissions.md). Untrusted project config contributes only deny/ask rules and non-security settings: it can't add allow rules or `additionalDirectories`, loosen the sandbox (`excludedCommands`, `allowedDomains`, `allowUnsandboxedCommands`), set `defaultMode` to `bypassPermissions`, or change provider base URLs. Trust decisions are stored in `<data>/trusted-folders.json` keyed by repo root, with the config file hash; a hash change asks again.

**Writes to settings files** (`/permissions`, "don't ask again", `/config`, migrations) are comment-preserving `jsonc-parser` edits written atomically (temp + rename, [tools §2.7](tools.md)), with arrays merged, never replaced. A settings file that is a symlink (dotfile managers such as stow or home-manager) is written at its target, and the link is kept.

**Format:** JSONC (comments and trailing commas allowed). A JSON Schema is published at `<repo>/schema/settings.schema.json`, referenced by `"$schema"` for editor completion. Unknown keys → warning with a "did you mean" suggestion (also how a file written by a newer Dovet is read by an older one). Invalid values are handled by the key's **kind**:
  - **Policy keys** (`permissions.*`, `sandbox.*`, `providers.*.apiKey`/`baseUrl`, `env`, budgets) → startup error naming file, line, key and expected type. Dovet never runs with part of the user's deny rules or budget silently missing.
  - **Other keys** (UI, retention, titles, …) → that key is ignored with a warning; the rest of the file still applies (one bad UI value must not disable a whole settings file).

**Reading settings files safely:** only regular files, at most 2 MiB (a `--settings` pointing at a device or a multi-GB file grew memory without bound). Numbers in settings and environment variables are parsed strictly: `1e6` means 1,000,000 or is rejected, never silently `1`; numbers given where strings are expected (`env` values) are converted, not crashed on. `retention.days` must be ≥ 1: turning off persistence is the `--no-session-persistence` flag, never a `0` that silently disables saving.

**`env` (subprocess environment):** `env: { "KEY": "value" }` in settings is added to the environment of **commands Dovet runs** (shell tools, v0.2 hooks/MCP), never to Dovet's own process. So `NO_COLOR` there doesn't change Dovet's UI. A variable already set in Dovet's launch environment wins, and `/status` lists the ignored keys. From **project** settings, `env` applies only in trusted folders, and these names are refused from project scope even when trusted: `PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_*`, `NODE_OPTIONS`, `BUN_OPTIONS`, `BASH_ENV`, `ENV`, `PROMPT_COMMAND`, `PYTHONSTARTUP`, `GIT_*`. Project settings never change anything outside that project (one project's setting must never disable a feature machine-wide).

**State files** (`trusted-folders.json`, sidecars, the budget ledger index) are validated on read. A corrupt one is **backed up** (`.corrupt-<time>`) and rebuilt with a warning, never discarded unrecoverably. They are written atomically under a lock.

## Data and privacy (what leaves the machine)

- **Prompts, files the agent reads, and tool output** go only to the provider and endpoint the user connected, and only in model requests. Each request is logged locally (`model.request`). What happens to it there follows that provider's own data policy (retention, training use, regional processing); `/status` links the provider's policy page from its registry record. Dovet sends OpenAI requests with `store: false`.
- **Dovet itself sends nothing else** except:
  1. the model-catalog refresh (an anonymous GET to models.dev);
  2. the update check (an anonymous GET to GitHub releases; `updates.check: false` turns it off);
  3. WebFetch requests, WebSearch queries (to the model provider or the chosen search service, [tools §10](tools.md)), and sandboxed commands' network traffic, all of which the user allows per host or per tool.
- No telemetry, no accounts, no automatic crash uploads (owner decision, 2026-10-12). `dovet bug` and `dovet doctor --report` prepare a report the user reads and sends themselves.
- `dovet --offline` disables (1) and (2) and refuses WebFetch/WebSearch; only model requests go out.
- Session logs, blobs and credentials stay on the machine (`<data>`, the keychain), user-only permissions ([event-log](event-log.md)).

## Two directory concepts (defined once, used everywhere)

| Term | Definition | Used for |
|---|---|---|
| **Working directories** | The **primary working directory** (where Dovet was started, or moved to with `/cd` in v0.2) plus additional directories (`--add-dir`, `/add-dir`, `permissions.additionalDirectories`) | Permission scope (reads without prompts, edits, sandbox write grants, `rm` critical paths), Bash cwd bounds |
| **Project root** | The git repository root containing the primary working directory (main checkout for worktrees); outside git, the primary working directory | `projectId` and session storage, where "don't ask again" rules are saved (`.dovet/settings.local.json` at the project root), workspace trust key, snapshots |

Starting Dovet in `repo/pkg/` makes `repo/pkg/` the working directory (edits in `repo/other/` prompt) while sessions, rules and trust belong to `repo/`. Instruction files are discovered from the filesystem root down to the primary working directory ([context §3](context.md)).

## Secrets

- **Resolution order** for a provider's credential (first match wins; `dovet auth status` shows which source is used and which are shadowed):
  1. `providers.<p>.apiKey` in settings, if set: a reference `env:VAR`, `keychain:<name>`, `cmd:<command>` (user settings only), or `none` (local servers);
  2. the credential stored by `/login` / `dovet auth login` in the OS keychain (API key or OAuth tokens);
  3. the provider's standard env var (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`/`GOOGLE_API_KEY`, `OPENROUTER_API_KEY`, …; listed in its registry record).

  There is no `--api-key` flag (keys on command lines leak into shell history and process lists).
- **Plain-text keys in config files are rejected** with an error explaining `dovet auth login`.
- Keychain: `Bun.secrets` (built into Bun; macOS Keychain, Windows Credential Manager with `persist: "local"`, Linux libsecret) [VERIFIED, Bun docs]. Service name `dovet`, entry name `<provider>`. If `Bun.secrets` fails a platform check in SPIKE-5, that platform uses `just-secrets` instead (same stores, through the OS's own `security`, `secret-tool` and PowerShell credential APIs; zero dependencies). Where no keychain exists at all (headless Linux without a Secret Service), credentials go to a file with mode 0600 in `<data>`; `/status` and `doctor` say so. Env-var keys work everywhere [SPIKE-5].
- Anthropic: if `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` are both set, the SDK sends both and the API rejects the request (401) [VERIFIED 2026-10-10]; Dovet detects this and tells the user.

## Startup sequence (interactive)

0. **No network on the startup path.** Every network call (catalog refresh, `models.retrieve`, update check) runs in the background with a 15 s timeout, so captive portals and firewalls never delay startup. The update check starts ~10 s after launch.
0b. **Unwritable config or data directory:** Dovet starts with in-memory config and data, says what can't be saved, and disables session persistence, instead of hanging on a blank screen. Failing session-log writes (disk full) are shown immediately, never silent.
0c. Variables that Dovet sets for its own child processes (`DOVET`, `DOVET_RUN`, `DOVET_SNAPSHOT`) are **ignored** when inherited at startup. A Dovet started inside a Dovet tool call says so instead of changing behavior (for example, it never stops saving sessions because of an inherited variable).
1. Parse arguments; load and validate settings (all scopes) — errors stop here with file/line/key.
2. Settings migration (below), if the settings `$version` is older.
3. Resolve provider and credentials. None configured → **first-run wizard** (interactive) or exit code 2 with setup instructions (headless / non-TTY).
4. **Workspace trust** dialog if the project supplies capability-granting settings ([permissions §11](permissions.md)); then the external-imports approval if needed ([context §3](context.md)); then a one-line notice of any Claude Code settings picked up (above).
5. Sandbox health check (cached per boot; ~50 ms), started in the background; the status bar shows `sandbox: starting` until it finishes, and the first shell command waits for it.
6. Load instruction files; build the epoch header; open or resume the session (lock).
7. Start the TUI. Background, non-blocking: model-catalog refresh, update check, Anthropic `models.retrieve` capability refresh.
Shell detection is cached per session; the environment snapshot starts in the background at session start ([tools §5.2](tools.md)). Target: steps 1–7 under 300 ms excluding dialogs (success metric in [vision](../product/vision.md)).

## Live settings reload

Before each user turn and each tool batch, Dovet **re-stats** every settings file in the precedence chain, plus the directories where one could appear, so a `.dovet/` folder created after startup is picked up. This uses `stat` polling, not OS file-event watchers: watchers miss changes when the OS event service is saturated and on network filesystems. A symlinked settings file is checked at its target. On a change:
- **Valid file:** permission rules, `additionalDirectories`, sandbox rules and other policy keys apply from the next tool call. Removed rules stop applying immediately, with no stale rules. Each change is logged as `settings.change` with `source: "file"` and shown as a one-line notice.
- **Keys that would change the model, provider, effort, thinking or the tool set** are **not** applied silently (principle 1). The notice names them, and they apply via `/model`, `/effort`, or at the next epoch boundary after confirmation.
- **Invalid file** (parse or schema error): the previous valid settings stay in force, with a warning naming file, line and key.
- **Grants from other sources survive:** removing a directory from `permissions.additionalDirectories` doesn't revoke the same directory added with `--add-dir` or `/add-dir`.
- Project settings changes from an **untrusted** folder are ignored, as at startup.

## Settings migration

Settings files carry an optional `"$version": <int>`. When a release renames or removes a key, it ships a migration step: Dovet shows the exact change ("`ui.fullscreen` → `ui.renderer: \"fullscreen\"`"), asks once to rewrite the file (keeping comments via `jsonc-parser` edits), and otherwise applies the mapping in memory with a startup warning. Removed keys produce a warning, never a silent ignore. Each migration has a test with a before/after fixture.

## Install, PATH and uninstall

- **POSIX install script** (`curl -fsSL https://…/install.sh | sh`): detects OS/arch/libc, downloads the archive and `SHA256SUMS` + signature, verifies both ([architecture](architecture.md)), unpacks to `~/.local/share/dovet/versions/<v>/`, points `~/.local/share/dovet/current` (symlink) at it, and creates `~/.local/bin/dovet` → `current/dovet`. If `~/.local/bin` isn't on PATH it **prints** the line to add; it never edits shell rc files. The signature is checked with OpenSSL 3 (on macOS the Homebrew `openssl@3` if the system's LibreSSL can't; each candidate must first pass an RFC 8032 test vector); with none, the script stops and says what to install (Q15). Installing over an existing install records the version `current` left in `previous`, as `dovet update` does.
- **Windows install script** (`irm https://…/install.ps1 | iex`): same verification; offers Git for Windows if it's missing ([platforms](platforms.md)); unpacks to `%LOCALAPPDATA%\dovet\versions\<v>\`; `%LOCALAPPDATA%\dovet\current` is a **directory junction** (no admin rights needed, unlike symlinks) to the version; adds `%LOCALAPPDATA%\dovet\current` to the **user** PATH (HKCU) after showing what it will change. Updating swaps the junction, so a running `dovet.exe` is never overwritten. Windows PowerShell 5.1 has no Ed25519, so the script verifies the signature with its own BigInteger code (RFC 8032), exercised in CI on a Windows runner against signed test releases.
- **`dovet uninstall`**: shows what will be removed (install dir, PATH entry/symlink, config, data incl. sessions — data and config are kept unless `--purge`), removes the Windows sandbox user if it was installed (`uninstallWindowsSandbox()`), and removes keychain entries on `--purge`.

## Piped input and non-TTY use

- `dovet -p "question"` with stdin piped (`cat log.txt | dovet -p "why does this fail?"`): stdin (max 10 MB, UTF-8) is attached as a text attachment named `stdin` before the prompt.
- `dovet -p` with no prompt argument reads the prompt from stdin.
- Interactive `dovet` with stdout not a TTY → error suggesting `-p`.

## Connecting providers: `/login`

Users never write provider configuration by hand. Every provider is a registry record: a **curated preset** (the versioned data file `ai/providers.jsonc` embedded in the binary: package, base URL, auth methods, key-validation call, model-listing call, docs link) or a record generated from models.dev ([providers "Provider registry"](providers.md)). Connecting one is a guided flow, available as `/login` in the TUI (alias `/connect`), as `dovet auth login [provider]` in the terminal, and as the first-run wizard. The `providers` settings key exists only to **override** a preset or add a custom endpoint.

**Flow (identical for every provider; driven by its registry record, [providers "Provider registry"](providers.md)):**
1. **Pick a provider** from the list (search by name), showing which are already connected and which are `tested` vs `community`.
2. **Pick a region and plan** when the record has several (e.g. Z.ai: International / China, Platform / Coding Plan), with a one-line hint about which console issues which key.
3. **Pick a method.** Only methods the provider **officially permits for third-party tools** are offered. The examples below reflect the registry's current entries (verified 2026-10-11); the registry is data and is revisited when policies change:

| Provider | Methods offered | Notes |
|---|---|---|
| Anthropic | API key (Claude Console) | Claude account (Pro/Max subscription) login is **not offered**: Anthropic's terms don't permit it for third-party tools. It is added only if Anthropic explicitly allows it or its terms change (re-checked before each release). The picker says so in one line |
| OpenAI | **Sign in with ChatGPT** (uses the user's ChatGPT plan; button text **Continue with ChatGPT**), or API key | Official for open-source apps that run locally (Dovet's case) [VERIFIED 2026-10-12, developers.openai.com/siwc]. Flow and request rules: "Sign in with ChatGPT" below |
| GitHub Copilot | Not offered | GitHub officially supports named partner tools only; other tools reuse a partner's OAuth client ID, which is impersonation. Offered only if GitHub approves Dovet's own OAuth app |
| Google | API key (AI Studio / Gemini API) | Google AI Pro/Ultra logins are **not offered**. Antigravity's Additional Terms (Antigravity CLI replaced Gemini CLI in June 2026) prohibit "using third party software, tools, or services to access the Service" with its OAuth |
| OpenRouter | Log in with browser (OpenRouter OAuth PKCE: localhost callback, `S256` challenge, code exchanged at `https://openrouter.ai/api/v1/auth/keys` for a user-owned API key) or paste a key | Officially documented for third-party and local CLI apps [VERIFIED 2026-10-12, openrouter.ai/docs/guides/overview/auth/oauth]; the result is an ordinary API key stored in the keychain |
| xAI | API key | SuperGrok login works only for xAI-allowlisted clients; other tools reuse xAI's own Grok-CLI client ID, which is impersonation. Offered only once xAI allowlists Dovet's own client |
| Vercel AI Gateway, Groq, DeepSeek | API key | AI Gateway has no subscription login; your own provider keys (BYOK) are configured in Vercel's dashboard, not in Dovet |
| Local (Ollama, LM Studio, vLLM) | None needed | Dovet **auto-detects** running servers on their default ports (11434, 1234, 8000) and lists their models |
| DeepSeek, Qwen (Alibaba), Kimi (Moonshot), GLM (Z.ai / Zhipu), MiniMax, ByteDance and others | API key per region and plan; coding-plan keys use the plan's endpoint (often Anthropic-compatible) and `plan` billing | Wrong-region keys are detected and the matching endpoint is offered |
| Other OpenAI-compatible | Base URL + optional key; Dovet probes `/v1/responses`, then `/v1/chat/completions`, and picks the protocol | Saved as a custom provider in user settings |

**Sign in with ChatGPT** (OpenAI's official flow for open-source local apps; [VERIFIED 2026-10-12, developers.openai.com/siwc]):
- **Host ID:** before the first sign-in, Dovet creates and stores one `ext_agent_host_id` per machine (`urn:uuid:<UUIDv4>`); it is an opaque identifier, never a secret, and is reused for every sign-in on that machine.
- **First sign-in (registers Dovet for that ChatGPT account):** start a listener on `http://127.0.0.1:<port>/auth/callback` (never `localhost`), then open the system browser at `https://auth.openai.com/api/accounts/authorize` with `client_id=dynamic_agent_client`, `agent_name_hint=Dovet`, the host ID, `response_type=code`, the exact `redirect_uri`, `scope=openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`, `resource=https://api.openai.com/v1`, fresh `state`, `nonce` and PKCE (`S256`). The callback returns `code`, `state` and the **issued** `client_id` (`oaiapp_…`), which Dovet saves for that account; `dynamic_agent_client` is never saved.
- **Token exchange:** form POST to `https://auth.openai.com/api/accounts/oauth/token` with the issued `client_id`, `code`, `code_verifier`, the same `redirect_uri` and `resource`; no client secret. The ID token is validated (signature against OpenAI's JWKS, issuer, audience = issued client ID, expiry, nonce). **Plan use is enabled only if the granted scopes include `chatgpt.tokens.use.direct`**; otherwise the login is kept but plan use is off, and Dovet offers to enable it (repeat OAuth with the full scope set) or to use an API key instead.
- **Later sign-ins:** the saved issued `client_id`, the same host ID, fresh state/nonce/PKCE, and the retained ID token as `id_token_hint`; no `agent_name_hint`.
- **Tokens:** access tokens last 1 hour, refresh tokens 30 days and rotate on every refresh. Dovet refreshes before expiry with the issued `client_id` and `resource` (no `scope`), serializes refreshes across processes with a lock (a rotating token must never be used twice), and stores the newest set. `invalid_grant`, `invalid_refresh_token`, `token_expired`, `refresh_token_expired`, `refresh_token_invalidated` or `refresh_token_reused` → clear the tokens and ask to sign in again. Temporary network errors never erase credentials.
- **Several ChatGPT accounts** are kept as separate registrations (each with its own issued client ID and tokens); `/login` shows the active one.
- **Sign out (`/logout openai`):** revoke the refresh token at the `revocation_endpoint` from `https://auth.openai.com/.well-known/openid-configuration`, then clear the tokens; keep the account's client ID and the host ID for a later sign-in. If revocation can't be confirmed, say so.
- **No browser (SSH, containers):** the loopback callback only reaches the machine running the browser, and there is no device flow. Sign in on a machine with a browser, then run `dovet auth export openai > file` there and `dovet auth import openai < file` on the remote machine over SSH; the import keeps the remote machine's own host ID. (Alternatively, forward the callback port: `ssh -L 1455:127.0.0.1:1455`.)
- **Models:** `GET https://api.openai.com/v1/models` with the access token lists the account's models; Dovet shows those with `visibility: "list"` (their `display_name`, using `slug` as the model ID), refreshed when the account changes.
- **Requests on the plan** (endpoint quirks in the provider record, [providers](providers.md)): `store: false`, `stream: true`, the full history in `input`; instructions via `instructions` or developer messages (system-role items are rejected); **never sent:** `max_output_tokens`, `prompt_cache_retention`, `temperature`, `top_p`, `truncation`, `metadata`, `safety_identifier`, `user`, `background`, `previous_response_id`; function tools are grouped in a tool namespace; image and file inputs work where the model accepts them; web search follows the account's policy.
- **Errors** (no silent switch to another billing method, principle 1):
  - `subscription_sharing_usage_limit_exceeded` (429): pause and show **Manage usage** (link to chatgpt.com/settings/usage); the limit may be the plan's or Dovet's own app limit.
  - `subscription_sharing_user_not_eligible` (403): explain the restriction and stop; no retries or OAuth loops.
  - `subscription_sharing_usage_unavailable` / `_user_unavailable` (503): retry with bounded backoff.
  - `subscription_sharing_unsupported_capability` (400): an adapter bug; name `error.param` in the error.
  - A pre-stream body like `{"detail": "…"}` (401/403/503) is shown as text.
- **UI:** the first time plan use is enabled, one notice: **You're using your ChatGPT plan** (Got it). While active, the status bar shows **Using ChatGPT plan**, and `/usage` links **Manage usage**. Plus plans share one five-hour limit across all apps; Pro has none.

4. **Credentials:**
   - **API keys:** typed in a masked field (never echoed or logged), checked with one cheap call (`models.list`), stored in the OS keychain (`Bun.secrets`, entry `<provider>`). Keys found in standard env vars are offered first ("Use `OPENAI_API_KEY` from your environment?").
   - **OAuth tokens:** access and refresh tokens are stored in the keychain. They refresh automatically before expiry, and a refresh failure asks the user to log in again (never a silent switch to another method). Without a browser (SSH, containers), Dovet offers the provider's **device code** where it has one, else prints the URL and accepts the pasted redirect URL or code.
   - **Key from a command** (user settings only; refused from project settings because it runs a program): `"apiKey": "cmd:op read op://dev/openai/key"` runs the command once when the key is first needed and keeps its output in memory for the session. That's how 1Password, `pass` and `security find-generic-password` users avoid storing keys twice. A non-zero exit, empty output or a 10 s timeout → a clear error naming the command, not the output.
   - **Why the keychain, not a file:** a plain JSON credentials file is readable by any process running as the user. Dovet uses the OS keychain and falls back to a file only where no keychain exists (see "Secrets" above).
5. **Pick a default model** from that provider's list (filtered to tool-capable models).

**Search services** appear in the same `/login` list under their own heading: Exa, Brave, Tavily (API key, stored the same way) and SearXNG (a URL, no key). They're used by WebSearch when the model's provider has no search of its own ([tools §10](tools.md)).

**Several providers at once:** any number can be connected; `/model` lists models grouped by provider. Long lists (OpenRouter, AI Gateway) can be narrowed per provider with `providers.<p>.models: { include: [...], exclude: [...] }` (glob patterns). Each provider remembers its method. `/logout [provider]` deletes the stored credential (and revokes OAuth tokens where the provider supports it). `dovet auth status` lists connections without showing secrets.

**Glass box for subscriptions:**
- **What is visible:** the status bar and every receipt state how a request is paid (`API key` vs `ChatGPT plan`).
- **Cost:** for plan-billed requests there is no per-token price. The cost meter shows tokens and `billed to plan allowance`, never an invented dollar figure.
- **Budgets:** dollar budgets don't apply to plan billing. A token budget (`budget.tokens`) can be set instead, and the first-run flow says so.
- **Allowance running out:** Dovet shows the provider's message and stops. It never falls back to API-key billing on its own (principle 1); `/login` can switch methods explicitly.

**Credential resolution order:** as in "Secrets" above (settings reference → `/login` credential → standard env var).

**Headless/CI:** environment-variable API keys only (`ANTHROPIC_API_KEY`, …), or a previously stored keychain credential. OAuth logins happen interactively; over SSH, `dovet auth login --device` works for providers with a device flow, and `dovet auth export`/`import` for the others (Sign in with ChatGPT).

## First-run wizard

Shown when no provider is connected (interactive only; headless exits with code 2 and instructions):
1. **Connect a provider:** the `/login` flow above (provider → region/plan → method → credential → check). Local servers that are already running are offered first, with "Use Ollama at localhost:11434 (3 models found)?".
2. Pick a model (from that provider's list, filtered to models with tool calling).
3. No budget is set by default (owner decision); the wizard says in one line that costs are shown live and `/budget` sets a limit.
4. Check the sandbox (the doctor's sandbox check). On Windows: MXC if available; otherwise offer `dovet sandbox install` (one-time administrator approval); and offer Git for Windows if missing ([platforms](platforms.md)).

- [ ] **AC-CLI-02** An untrusted project's allow rules are ignored; deny rules apply.
- [ ] **AC-CLI-03** A plain-text key in config fails startup with the documented message.
- [ ] **AC-CLI-04** `dovet doctor` passes on clean CI images for all three OSes, and reports each injected failure (missing bwrap, missing rg, bad config).
- [ ] **AC-CLI-05** Startup order: with a project needing trust and no provider configured, the wizard runs before the trust dialog, and the trust dialog before the session opens; headless with no provider exits 2 with instructions.
- [ ] **AC-CLI-06** A settings file using a renamed key is migrated on confirmation with comments preserved; declining applies the mapping in memory with a warning.
- [ ] **AC-CLI-07** POSIX install script never edits rc files; Windows install updates only the user PATH; `dovet update` on Windows swaps the junction while an older `dovet.exe` is running.
- [ ] **AC-CLI-08** `dovet uninstall` keeps config and data by default and removes them (and keychain entries) only with `--purge`.
- [ ] **AC-CLI-09** `cat file | dovet -p "q"` attaches stdin as `stdin`; `dovet -p` with no argument reads the prompt from stdin.
- [ ] **AC-CLI-10** Started in `repo/pkg/`: an edit in `repo/other/` prompts; "don't ask again" saves to `repo/.dovet/settings.local.json`; the session is stored under `repo`'s projectId.
- [ ] **AC-CLI-11** An invalid `ui.theme` value is ignored with a warning while the file's deny rules apply; an invalid `permissions.deny` entry stops startup with file, line and key; `DOVET_BUDGET=1e2` means 100; a 3 MB settings file and a FIFO in its place are rejected clearly.
- [ ] **AC-CLI-12** `env` from user settings reaches a Bash command but not Dovet's own UI; a launch-environment value wins and is listed in `/status`; project `env` with `PATH` or `LD_PRELOAD` is refused even in a trusted folder.
- [ ] **AC-CLI-13** Startup with the network blackholed reaches the prompt in under 1 s; with a read-only `<data>`, Dovet starts and says sessions won't be saved; a corrupt `trusted-folders.json` is backed up and rebuilt; `DOVET_RUN` inherited from a parent Dovet doesn't change behavior.
- [ ] **AC-CLI-14** Internal git calls in a partial clone trigger no fetch, in a repo with a nested filter-configured repo run no filter, and never open a credential prompt (marker-file tests).
- [ ] **AC-CLI-15** `/login` drives every provider from its registry record: a curated provider (Anthropic), a models.dev-derived community provider, a region/plan choice (Z.ai International Coding Plan), a local server found by port probe, and a custom endpoint all complete with the same code path (fixture servers); a China-platform key entered for the international endpoint is detected and the China endpoint is offered.
- [ ] **AC-CLI-16** Plan billing: a request on a `plan`-billed endpoint shows tokens and `billed to plan allowance` in the meter and receipt, no dollar figure; a `budget.tokens` limit stops the session; plan exhaustion stops with the provider's message and no automatic switch to API-key billing.
- [ ] **AC-CLI-17** Credentials: an API key never appears in the log, the transcript or the terminal scrollback; `cmd:` keys are refused in project settings; `dovet auth status` shows the resolution source for each provider without secrets.
