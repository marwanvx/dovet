**Foundation [ADR-28]:** Dovet decides on an action's **effects**, and the boundary is enforced by the OS sandbox plus checkpoints. It asks at the edge of reversibility, not on every command (§0b).

**Compatibility [ADR-18]:** rule syntax, mode names, settings keys and prompt options are compatible with Claude Code's documented permission system [VERIFIED 2026-10-11], so existing rules and settings import unchanged ([cli-config "Coming from Claude Code"](cli-config.md)). The rules are how users *express* policy; what Dovet decides on is the effect.

Three layers, all enforced in code (principle 9):
1. **Permissions** — should this tool call happen? (rules + mode + built-in safety checks + user decision)
2. **Sandbox** — when a shell command runs, what can it touch? (OS-enforced)
3. **Taint** — has untrusted content entered the session? If so, tighten 1 and 2.

## 0. Threat model

**Untrusted input classes:** everything the model reads that the user didn't type in this session: repository files (including README, AGENTS.md/CLAUDE.md from cloned repos, code comments, test fixtures), command and test output, diffs, web pages and search results, MCP results (v0.2), filenames, git metadata (commit messages, branch names).

**Guarantees (enforced by code, independent of what the model decides):**
1. Project content can't change Dovet's policy: project settings that grant capability need workspace trust (§11); protected paths block writes to settings, hooks and shell startup files (§4.3, §7.2).
2. Credentials can't be read by Dovet's own tools without an explicit user approval (§4.7) or by sandboxed commands from the home-directory credential list (§7.2).
3. External effects (network to unapproved hosts, writes outside working directories, unsandboxed commands, push/publish) need either an explicit allow rule or a user prompt; a tainted session (§10) blocks the riskiest ones outright.
4. Critical-path removals can never be approved by rules or hooks (§4.4).

**Terminal injection:** text Dovet didn't author is sanitized before it reaches the terminal, so model or tool output can't set the title, write the clipboard, plant deceptive links or fake UI ([tui Terminal output sanitization](tui.md)).

**Binary planting:** programs Dovet spawns are resolved to absolute paths outside the project, and UNC paths are refused ([platforms](platforms.md)), so a repository can't plant `git.exe` or trigger NTLM credential leaks.

**Trusted, outside the model:** the process environment Dovet is started with. Compiled Bun executables still honor `BUN_OPTIONS` (e.g. `--preload <file>` runs code before Dovet's entry point) and `BUN_BE_BUN=1` (the binary behaves as the `bun` CLI) [VERIFIED 2026-10-11, Bun docs]. These are read before any Dovet code runs, so Dovet can't block them, just as Node CLIs can't block `NODE_OPTIONS`. A directory-scoped env loader (direnv, mise) that sets them would run project code. Mitigation: at startup Dovet warns once if `BUN_OPTIONS` or `BUN_BE_BUN` is set; `dovet doctor` reports them; child processes get both removed from their environment.

**Not guaranteed:** that the model won't be *persuaded* by injected text to do something within its allowed permissions (e.g. edit files in the workspace wrongly, or run an allowed command). Taint is a coarse session-level tripwire, not a prompt-injection solution. The eval suite includes adversarial tasks: injected instructions in README/AGENTS.md of a cloned repo, in test output, in a fetched page, and in a diff ([testing](testing.md)).

## 0b. The boundary: what runs freely and what asks [ADR-28]

| Effect | Reversible? | Behavior |
|---|---|---|
| Edits inside working directories | Yes: checkpoints ([checkpoints](checkpoints.md)) | Sandboxed shell commands: free. Edit/Write tools: free in `acceptEdits`; in Manual mode they prompt as the user's **review preference** (shown as "Review edit"), not as a safety check |
| Reads inside working directories, except sensitive files | Nothing changes | Free |
| Reads outside working directories | Nothing changes, but data outside the project becomes visible to the model | Dovet's file tools ask (§4.1); sandboxed commands may read outside except credential paths (sandbox default, §7.2) |
| Reads of credential/sensitive paths | No (data can leave later) | Ask (§4.7); denied to sandboxed commands (§7.2) |
| Network to allowed hosts (package registries, approved domains) | Partly: an allowed host is still a channel | Free; taint suspends it (§10) |
| Network to a new host | No | Ask (§7.4) |
| Writes outside working directories; protected paths; critical-path removals | No | Ask (§4.1, §4.3, §4.4) |
| Unsandboxed execution (retry, excluded command, no sandbox available) | Unknown effects | Ask unless a read-only command or an explicit allow rule (§7.5); the status bar says commands are judged by their text |
| Recognized remote actions: `git push`, publish/upload/deploy commands, (v0.2) MCP tools annotated `destructiveHint` | No | Ask via the built-in remote-action list (§4.8), even sandboxed and even if the host is allowed; denied while tainted (§10); force-push to the default branch denied (§5) |

**Every prompt names its boundary.** The prompt's reason line says which row it protects (`new network host: api.example.com`, `write outside the project: ~/.bashrc`). A new kind of prompt must fit a row above, or the user's review preference; otherwise it isn't added. Prompts that guard nothing teach users to approve blindly.

## 1. Tool categories and default behavior (Manual mode)

| Tool type | Example | Approval needed | "Yes, and don't ask again" saves |
|---|---|---|---|
| Read-only | Read, Grep, Glob | No, inside working directories | — |
| Shell | Bash, PowerShell | Yes, except built-in read-only commands (§4.6) — and see sandbox auto-allow (§7.3) | A rule per subcommand, permanently, in local settings |
| File modification | Edit, Write | Yes | **Session only** (not saved to a file) |
| Web fetch | WebFetch | Yes | A `WebFetch(domain:…)` rule, permanently, in local settings |

**Permanent rules are saved** to `.dovet/settings.local.json` at the **git repository root** (resolved through worktrees to the main checkout), so they apply in subdirectories and worktrees. Outside a git repo: the starting directory. The file is created if it doesn't exist and added to `.git/info/exclude`, so it is never committed and the repo's `.gitignore` is never changed. Session-only grants are never written to it.

**Decided while building (QUESTIONS Q43):**
- "Don't ask again" suggestions: `Edit(<working directory>/**)` for an edit inside a working directory with no finding; the exact file for one outside it or on a sensitive file. `Bash(<program> <verb> *)` for version-control, package and cloud tools (`git`, `npm`, `cargo`, `kubectl`, …), `Bash(<program> *)` for other programs, the exact command for shells, `sudo`/`env`/`xargs`, destructive programs (`rm`, `mv`, `chmod`, …) or an argument containing `*`. At most 5 rules; none when the call has an unlifted safety ask or invisible characters, or a generated rule doesn't match its own subcommand.
- For a non-sensitive read outside the working directories, "don't ask again" saves a permanent `Read(<directory>/**)` for that file's directory (the exact file for the home directory or the filesystem root).
- Rule anchors: project, local and `.claude/` project files and `env`/`flags` anchor at the primary working directory; `user` at the Dovet config dir; `claude-user` at `~/.claude`.
- Effects of a shell call: only read-only commands is none/none; unsandboxed is `unknown` writes and network; sandboxed takes workspace/outside/protected from the findings and network `allowed-hosts`. Every save re-checks `.git/info/exclude`.

## 2. Permission modes

Mode names are the same config values as Claude Code's, so settings import directly.

| Mode | Runs without asking | Notes | Release |
|---|---|---|---|
| `default` (shown as **Manual**) | Reads in working directories; read-only shell commands; sandboxed shell commands when sandbox auto-allow is on (§7.3) | The default for new users | v0.1 |
| `acceptEdits` | + file edits in working directories, and filesystem commands `mkdir`, `touch`, `rm`, `rmdir`, `mv`, `cp`, `sed` on in-scope paths (PowerShell: `Set-Content`, `Add-Content`, `Clear-Content`, `Remove-Item` on in-scope paths) | Protected paths and critical-path removals still prompt | v0.1 |
| `plan` | Reads, built-in read-only commands, and writes to the session's own plan file ([tools §11](tools.md)) | All other edits blocked until the user approves the plan; other commands prompt (headless: denied). Sandbox auto-allow does **not** apply in plan mode | v0.1 |
| `dontAsk` | Same as `default`, but everything that would prompt is **denied** | For CI/headless; never waits for input | v0.1 |
| `bypassPermissions` | Everything except the actions in §5 | Only for containers/VMs. Disable with `permissions.disableBypassPermissionsMode: "disable"` | v0.1 |
| `auto` | Like `acceptEdits`; boundary crossings (§0b) are reviewed by a **model** instead of the user | A model call per reviewed action (costs tokens, shown and counted). See §9 | **v0.2** |

- **Name:** `default` is shown as **Manual**, and `"manual"` is accepted as an alias in settings and `--permission-mode`.
- **Mode changes only by explicit user action.** No approval, plan exit or protected-path write ever lowers or raises the mode silently. Leaving plan mode offers to **return to the mode that was active before plan** (e.g. `bypassPermissions`) as the first choice, never a lower one.
- **Plan mode overrides allow rules for mutations:** in `plan`, no allow rule, sandbox auto-allow or `acceptEdits` behavior permits file writes or non-read-only commands. Read-only tools and commands are auto-allowed from the first turn, including when the session starts in plan mode. These blocks apply in every session, including sessions started with bypass permissions: plan mode means nothing changes until the plan is approved. A user who wants changes without a plan leaves plan mode (Shift+Tab). Plan mode persists across compaction, every resume path, and forks; a fork or (v0.2) subagent inherits the parent's plan mode and cannot leave it.
- **A mode switch while a prompt is open** re-evaluates it: if the new mode permits the call, the prompt closes and the call runs.
- **Cycling:** `Shift+Tab` cycles `default → acceptEdits → plan → (auto, when available) → default`. `bypassPermissions` only via `--permission-mode bypassPermissions` / `--dangerously-skip-permissions`.
- **Starting mode:** `permissions.defaultMode` in settings; otherwise `default`. With a working sandbox, `default` already avoids most prompts (§7.3).
- The current mode is always visible in the status bar.

**Decided while building (QUESTIONS Q42):** in plan mode an edit or a non-read-only command is denied, not asked: nothing changes until the plan is approved. Under sandbox auto-allow, sandboxed commands are free (§0b); sensitive paths still ask. `sed` with `e`/`w`/`-f` and `cp -t` are not acceptEdits file commands.

## 3. Rules

### 3.1 Syntax and evaluation
- Format: `Tool` or `Tool(specifier)`. Parentheses inside the specifier are literal. `Bash(*)` ≡ `Bash`.
- **Robust rule loading:**
  - text after the closing parenthesis (`Bash(ls) x`) is an invalid-settings error naming file and line, never silently ignored;
  - a rule containing a NUL byte matches nothing;
  - a path pattern that can't compile (e.g. unclosed `[`) in a **deny/ask** rule guards the literal path it spells, and in an allow rule it is ignored with a warning; it never breaks every file operation;
  - rules live in `Map`s, never plain objects, so names like `toString` or `__proto__` can't make a settings file be silently ignored;
  - matchers are compiled once per settings load and cached (per-turn slowdowns with many rules).
- **Unreachable-rule detection:** at load and in `/doctor`, Dovet warns about rules that can never take effect, naming the shadowing rule and its source file (e.g. an allow fully covered by a deny).
- Arrays: `permissions.allow`, `permissions.ask`, `permissions.deny`.
- **Evaluation order: deny → ask → allow. The first match wins**; specificity does not matter. A broad deny (`Bash(aws *)`) beats a narrower allow (`Bash(aws s3 ls)`); a matching ask beats a matching allow.
- A bare tool name in **deny** (`Bash`, `Bash(*)`, `WebFetch`) **removes the tool from the model's context** at the next epoch start; mid-epoch it blocks every call (tools can't be removed mid-epoch without breaking the append-only prefix — [context](context.md)).
- **Parameter rules** (deny/ask only): `Tool(param:value)` matches a top-level scalar input parameter, `*` wildcard allowed, e.g. `Bash(dangerouslyDisableSandbox:true)`. Rules on a tool's primary field (`command`, `file_path`, `path`, `url`) are rejected at startup with a warning (bypassable via compound commands).
- Tool-name globs: deny/ask accept `"*"`, `"mcp__*"`; allow accepts globs only after a literal `mcp__<server>__` prefix.
- Unknown tool names in deny/ask → startup warning (catches typos).
- **Rule examples:** `permissions.examples` lists commands or tool calls with the decision the user expects, e.g. `{ "Bash": "git push --force origin main", "expect": "deny" }`. They are checked at load and by `dovet doctor`, and a mismatch is reported naming the rule that actually decides. Rules are tested the way users intend them, and a misread rule (§3.2's literal-prefix pitfalls) shows up before it matters.

**Decided while building (QUESTIONS Q40):**
- `name:value` is a parameter rule only when `name` is a primary field (rejected with a warning) or listed in `RuleContext.toolParams` for that tool; otherwise it is shell text.
- One allow rule must cover every path of the call, each in both spellings (requested and canonical). A Read allow never covers an edit.
- Path rules compile to gitignore patterns under absolute roots (the literal directory prefix and its canonical form). A `!` rule re-includes only against earlier rules of the same file, behavior and tool. `lib/` and `lib/**` float (a `**/` prefix) in deny and ask, and are anchored in allow; an unclosed `[` is an escaped literal in deny and ask.
- A rule is reported unreachable when an earlier-priority rule of the same tool is bare, has an equal path text, or its shell pattern matches the later rule's pattern text. PowerShell rules are case-insensitive.

### 3.2 Shell rules (Bash and PowerShell)
- `*` matches any text **including spaces**; a rule without `*` matches exactly one command.
- Everything before the first `*` is matched literally: `Bash(git log *)` allows only `git log …`; `Bash(git *)` allows every git command. Startup warning for an allow rule with `*` before the subcommand (`Bash(git * main)`).
- A trailing ` *` (space + star) also matches the bare command (`Bash(ls *)` matches `ls`, not `lsof`); `Bash(ls*)` matches `lsof` too. `:*` is equivalent to ` *` **anywhere** in the pattern, with a startup warning explaining the match.
- Matching is done on the **parsed argv**, re-joined with single spaces: extra spaces or tabs, and quoted `#` or `-` inside arguments, don't defeat a rule. Output redirections are not part of the matched text (`Bash(python *)` matches `python x.py > out.txt`); redirect targets are checked separately by path policy (§4.5).
- **Compound commands:** separators `&&`, `||`, `;`, `|`, `|&`, `&`, newline. **Each subcommand must match an allow rule independently.** Deny and ask rules match if **any** subcommand matches, including inside subshells, `$( )`, backticks, process substitution, and control-flow bodies. A dangling `&&`/`||` makes the command unparseable (no allow match).
- **Loops over globs** (`for f in *.ts; do …; done`) are parsed as control flow: the loop body's commands are checked like any subcommand, and the glob is expanded by Dovet for file-operand checks (§4.0 item 4).
- "Don't ask again" on a compound command saves **one rule per subcommand that needed approval** (max 5).
- **Stripped wrappers** before matching: `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, zsh `noglob`, flagless `xargs`, and leading assignments of known-safe env vars (allow rules); deny/ask rules match past **any** leading assignment **and** past exec wrappers (`env`, `sudo`, `doas`, `watch`, `ionice`, `setsid`, `flock`, `xargs`, `nice`, `timeout`): a deny on `rm` also catches `sudo rm` and `env X=1 rm`. Not stripped: `command -v`, `direnv exec`, `npx`, `docker exec`, `devbox run`, … (they run arbitrary commands, so they need explicit rules).
- **Never auto-approvable by prefix rules:** exec wrappers (`watch`, `setsid`, `ionice`, `flock`) and `find` with `-exec`/`-execdir`/`-ok`/`-delete`/`-fprint*`/`-files0-from`. The same goes for flags that change *where* or *how safely* a command acts: `docker`/`podman` daemon redirects (`-H`/`--host`, `--context`, `--url`, `--connection`, `--identity`, Podman remote mode), and `git`/`gh` with `--force*`, `--no-verify` or `--amend`. Only an exact-match rule (no `*`) approves them.
- **PowerShell:** same shapes; common aliases canonicalized (`gci`/`ls`/`dir` → `Get-ChildItem`); case-insensitive; AST split on `|`, `;`, and `&&`/`||` (PowerShell 7+).
- **Honest limit (documented to users):** shell rules match the command *text*. `Bash(git push *)` doesn't stop `git -C . push` or `sh -c 'git push'`. Deny/ask rules are guardrails against model mistakes, **not a security boundary**; the sandbox is.

### 3.3 File rules (Read and Edit)
- Only `Read(path)` and `Edit(path)` are consulted for files. `Edit` rules cover Edit and Write. A `Write(path)`/`Glob(path)` rule triggers a startup warning telling the user to use `Edit`/`Read`.
- A `Read` deny also blocks edits and writes on that path.
- gitignore pattern syntax. Anchors:

| Pattern | Means |
|---|---|
| `//path` | Absolute from filesystem root |
| `~/path` | From home directory |
| `/path` | Relative to the **settings source**: project/local settings → primary working directory; user settings → the Dovet config dir; `--settings <file>` → that file's directory |
| `path`, `./path` | Relative to the current directory |

- Single-segment directory patterns: in **allow** rules, `src/**` matches only `<cwd>/src`; in **deny/ask** rules, it matches a `src` dir at any depth. Bare filenames match at any depth.
- `!pattern` in deny/ask = gitignore negation, only against earlier rules from the same source.
- Approved paths saved by "don't ask again" have gitignore metacharacters escaped.
- **Windows:** paths are normalized to POSIX form before matching (`C:\Users\a` → `/c/Users/a`); matching is case-insensitive; rules written with backslashes (`~\Documents`), drive letters in either case, or scoped to a drive root (`C:\`) work as written.
- **Symlinks:** a path matches a rule if **either** its requested spelling **or** its canonical target matches, and rule paths themselves are also canonicalized. So `Read(/etc/**)` still applies on macOS, where `/etc` is `/private/etc`, and a link inside the project to an outside file is judged by where it lands. Deny/ask take effect if either form matches; allow requires the canonical target to be allowed.
- Read/Edit deny rules also apply to recognized file commands in shell (`cat`, `head`, `tail`, `sed`, `tee`) and to redirection targets; **not** to arbitrary programs that open files themselves (the sandbox covers those).

### 3.4 WebFetch rules
- `WebFetch(domain:example.com)` matches exactly that host; `WebFetch(domain:*.example.com)` matches subdomains (not the apex); `WebFetch(domain:*)` matches all. Elsewhere `*` matches only within one label (`example.*` matches `example.org`, not `example.evil.com`). Case-insensitive; trailing dot stripped.
- Explicit `WebFetch(domain:…)` deny/ask rules **override** built-in pre-approved domains.
- Bare `WebFetch` (no `domain:`) in allow = fetch freely **without** widening the sandbox; `WebFetch(domain:…)` allow rules **also add the domain to the sandbox network allowlist** (§7.4).

### 3.5 MCP rules [v0.2]
`mcp__server` / `mcp__server__*` (all tools of a server), `mcp__server__tool` (one tool).

## 4. Built-in safety checks (independent of rules)

### 4.0 How shell commands are analyzed
Text-based command checkers keep being bypassed by new shapes (special variables such as `BASH_ARGV0`, `BASHPID`, `OPTIND=1/0`; zsh `REPORTTIME` and `[[ ]]` regex/subscripts; declaration flags; backslash-escaped flags; fd-redirect forms; crafted commands hiding parts of themselves). Dovet follows principles instead of a list of patches:
1. **Auto-approval needs full understanding.** Every syntax node of the parsed command (tree-sitter) must belong to an explicit **allowlist of understood constructs**: simple commands with literal or simply-quoted words, the separators of §3.2, pipes, `cd`/`pushd`/`popd` with literal targets, plain redirects to literal paths, quoted heredocs, unquoted heredocs whose body holds only plain text and simple `$VAR` references, and assignments to allowlisted variable names (`LANG`, `LC_*`, `TZ`, `NO_COLOR`, `CI`, `FORCE_COLOR`, `DEBUG`, `NODE_ENV`, …). Anything else makes the command **"not fully checkable"**: arithmetic expansion or arithmetic assignments, parameter expansion with operators or modifiers, special shell variables, `eval`, `source`, `exec`, `env -C`, process substitution, `coproc`, function definitions, unrecognized fd-redirect forms, non-literal `cd` targets, and any parse error. Read-only status and allow rules then **don't apply**, and the user is asked. **Under sandbox auto-allow (§7.3) the bar is lower**, because the sandbox is the boundary: a sandboxed command runs unprompted as long as every **command-name position is literal**, so deny/ask rules and critical-path checks can still be evaluated. Expansions (`$VAR`, `$(…)`), inline scripts (`python3 -c "x=1"`, `node -e …`), heredocs piped to interpreters and env-prefixed interpreters (`FOO=bar python3 app.py`) don't make it prompt. Only a dynamic command name (`eval "$x"`, `$cmd args`, `sh -c "$script"` with a non-literal script, `xargs` running a computed command) still asks. Deny rules and critical-path checks still apply to every part that *can* be read. Unanalyzable lines **prompt rather than deny**.
2. **Analyze what will run.** Model commands always execute in **bash** ([tools §5.3](tools.md)), the language the analyzer parses. zsh's different word splitting, glob qualifiers, `[[ ]]` semantics and special parameters are a known source of bypasses.
3. **Read-only commands are described as data,** each with the options it accepts and which arguments and options take **file paths** (positional operands, `--ignore-revs-file=`, `-f FILE`, `@file`, `git diff`/`git grep` paths, …). An **unrecognized option** makes the command not read-only (fail closed).
4. **Every file operand is checked:** literal ones, the files an unquoted glob in a file position expands to (Dovet expands it itself; more than 1,000 matches → ask), and option-value paths. All are checked against Read/Edit deny rules, the outside-working-directory block, sensitive files (§4.7) and UNC refusal. An unquoted glob in a **pattern** position (`rg foo*`, `git grep a*`), which the shell would expand into file names, → ask.
5. **cwd is simulated** through `cd`/`pushd`/`popd` along a compound command, so `cd DIR && cat FILE` resolves `FILE` in `DIR`. A no-op `cd` into the current directory, or into the project, doesn't by itself cause a prompt. Variables like `PWD`/`OLDPWD` are never trusted from earlier tracking.
6. **A safety finding in any part flags the whole command,** regardless of other parts: e.g. a critical `rm` stays "always ask" even when the same line also redirects to `~`, and an ask rule or safety check inside a compound command can't be bypassed in any mode.
7. **The analyzer fails closed:** a parser that fails to start or times out (out of memory, a pathological input) yields "not fully checkable", never a cached allow. Analysis has a 200 ms budget per command.
8. Commands over 10,000 characters are never auto-approved, for Bash and PowerShell alike.

**Decided while building (QUESTIONS Q41):**
- `analyzeShell(parsers, language, command, opts)` returns `{ commands, understood, literalNames, reasons, operands }`. `commands` are the simple commands anywhere in the text (`{ argv, redirects?, readOnly? }`, redirect targets made absolute in the simulated cwd), or undefined when the text couldn't be parsed (an error, the 200 ms timeout, a crash). `understood` is false when any node is off the allowlist or the text is over 10,000 characters; then no allow rule applies (`RuleCall.checkable`). A subcommand with `readOnly: true` needs no allow rule of its own.
- A `$( )` or backtick inside a word is understood when its own commands are, and makes the word non-literal; process substitution is not understood. `sh|bash|zsh|dash|ksh -c <literal>` is parsed as a nested script (depth 8) so deny and ask rules see its commands, but the call is never understood.
- `tee` targets are `edit` operands (not understood with `~` or a glob).

### 4.1 Working directories
- Definitions of **working directories** and **project root**: [cli-config](cli-config.md) "Two directory concepts". Primary working directory = where Dovet started (moved with `/cd`, v0.2). Add with `--add-dir`, `/add-dir`, or `permissions.additionalDirectories`.
- Reads inside working directories need no approval (except sensitive files, §4.7). Reads by Dovet's file tools **outside** working directories ask (reason `outside working directory`); "don't ask again" saves a `Read(<dir>/**)` rule. `permissions.blockReadsOutsideWorkingDirectories: true` makes file tools refuse outside reads in every mode.
- **Network and device paths** (Windows UNC `\\server\share`, `\\?\UNC\…`, `\\.\` device paths; `/net/<host>` automounts): Dovet's file tools and working directories **refuse** them without looking them up, in every mode ([platforms](platforms.md)); touching one makes Windows send the user's NTLM credentials to that server. A shell command with a network-path argument asks (reason `network path`) and is denied in `dontAsk`; no rule pre-approves it.

### 4.2 Symlinks
- Permission checks evaluate **both** the requested path and its resolved target. Allow applies only if **both** match; deny applies if **either** matches.
- Edit/Write refuse when the target path itself is a symlink (the tool tells the model the real target).
- After approval, the tool re-verifies the path still resolves to the approved location before opening (TOCTOU guard). Loops / unresolvable paths → refuse.

### 4.3 Protected paths
Writes are **never auto-approved** in any mode: they prompt in `default`/`acceptEdits`/`plan` **and in `bypassPermissions`**, and are denied in `dontAsk`. Allow rules do not pre-approve them.
- Directories: `.git`, `.config/git`, `.vscode`, `.idea`, `.husky`, `.cargo`, `.devcontainer`, `.yarn`, `.mvn`, `.dovet` and `.claude` (except Dovet's own plan/scratch files).
- Files: `.gitconfig`, `.gitmodules`, shell startup files (`.bashrc`, `.bash_profile`, `.bash_login`, `.bash_aliases`, `.bash_logout`, `.zshrc`, `.zprofile`, `.zshenv`, `.zlogin`, `.zlogout`, `.profile`, `.envrc`), `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `.pnp.cjs`, `.pnp.loader.mjs`, `.pnpmfile.cjs`, `bunfig.toml`, `.bunfig.toml`, `.bazelrc`, `.bazelversion`, `.bazeliskrc`, `.pre-commit-config.yaml`, `lefthook.y(a)ml`, `.lefthook.y(a)ml`, `gradle-wrapper.properties`, `maven-wrapper.properties`, `.devcontainer.json`, `.ripgreprc`, `pyrightconfig.json`, `.mcp.json`, `.claude.json`.
- Why: writing these could grant the agent new permissions or run code outside the sandbox (hooks, MCP servers, shell startup).
- The list is a versioned data file in `policy/`, with tests.

### 4.4 Critical paths (`rm`, `rmdir`, `Remove-Item`)
A circuit breaker against model error. **No allow rule or hook can approve** a removal targeting a critical path:
- Filesystem root and its direct children (`/usr`, `/etc`, …; on macOS also `/private/etc`, `/private/var`, `/private/tmp`, `/private/home`); home directory, in every spelling: `~`, `$HOME`/`${HOME}` even with a trailing slash in `HOME`, Git Bash `/c/Users/<name>` and `/cygdrive/c/…`, Windows 8.3 short names and other alternate spellings, canonicalized with the long path name before comparing; drive roots and their top-level dirs (`C:\`, `C:\Windows`, incl. `\\?\C:\`, `\\localhost\C$`); the working directory and its parents; additional directories and parents (for globs under them).
- Also critical: a glob/trailing slash directly under a shell variable (`rm -rf "$DIR"/*`), under an unset positional parameter, a variable + common top-level name (`"$TMPDIR/mnt"`), a variable assigned from `$(pwd)`/`$(git rev-parse --show-toplevel)`, a recursive `rm` whose target is only a command substitution, a critical path followed by a substitution (`~/$(cmd)`), a backslash-only target, volume-GUID paths, and some `/*`-ending forms whose reach can't be determined.
- Detection looks inside subshells, groups, substitutions, and `sh/bash/zsh -c` inline scripts (double-quoted scripts expand variables first).
- Sandbox auto-allow never skips this check.
- Outcome: prompt in `default`/`acceptEdits`/`plan`/`bypassPermissions`; denied in `dontAsk`. In `bypassPermissions` the prompt has a 2-minute countdown; on timeout it's denied and the model is told to leave the removal to the user; after 3 timeouts per session, further ones are denied immediately.
- **PowerShell analysis:**
  - built-in `cd` variants (`cd ..`, `cd\`, `cd~`) and drive switches (`X:`) are tracked as `cd`;
  - assignments to `$PSDefaultParameterValues` and other preference variables, and parameters that write variables (`-OutVariable`, `-ErrorVariable`, `-WarningVariable`, `-InformationVariable`, `-PipelineVariable`), make a command not fully checkable;
  - a trailing `&` (background job) and `-ErrorAction Break`/`-Debug`, which can hang on a debugger prompt, are never auto-approved;
  - `Expand-Archive` and other archive extraction are treated as writes to every entry's destination;
  - paths containing quote characters → ask;
  - a bare `--` is not the `--%` stop-parsing token.
- **PowerShell `Remove-Item`:** system paths and bare-`*` or `/*`/`\*` wildcard targets are **denied in every mode**; working dir or parents with `-Recurse` → normal approval flow. Same for `cmd /c rd|rmdir|del|erase` on system paths.
- The prompt explains how to rewrite a flagged command (e.g. `rm -rf "${DIR:?}"/*`).

### 4.4b Self-protection and process control
- `kill`/`taskkill` targeting Dovet's own PID or its parent → denied. `pkill`/`killall` (and `Stop-Process -Name`) whose pattern could match Dovet's own process name or command line → ask, with that warning.
- Shell commands that write to files Dovet's file tools would refuse (the credentials file, keychain exports, sensitive files of §4.7) → ask, even under a whole-tool `Bash` allow rule.

### 4.5 Redirections and `tee`
- Output redirects (`>`, `>>`, `2>`) and `tee` targets are checked like an Edit of that path (Edit rules, protected paths, working directories). Targets with `~` or globs need approval.
- Input redirects (`<`) are checked like a Read.
- Not checked: `/dev/null`, `NUL`, fd forms (`2>&1`), here-docs/here-strings.

### 4.6 Built-in read-only commands
Run without prompting in every mode (unless an ask/deny rule matches, or §4.0 says the command isn't fully checkable): `ls`, `cat`, `echo`, `printf`, `pwd`, `head`, `tail`, `grep`, `rg`, `fd`/`fdfind`, `find` (no action flags), `wc`, `which`, `diff`, `cmp`, `comm`, `stat`, `du`, `df`, `file` (without `-m`/`-f`), `tree`, `cd` (into working dirs), `date`, `uname`, `true`, `false`, `test`, `expr`, `seq`, `fmt`, `numfmt`, `tsort`, `pr`, `getconf`, `tput`, `lsof`, `pgrep`, `ss` (`pyright` and env-printing `ps` forms are not included; `help`/`man` only without options), and read-only `git` forms (`status`, `diff`, `log`, `show`, `branch` list forms, `rev-parse`, `ls-files`, `blame`). PowerShell: `Get-ChildItem`, `Get-Content`, `Get-Location`, `Select-String`, `Get-Item`, `Test-Path`, `Measure-Object`.
Bare assignments (`FOO=bar` on its own) are read-only only for allowlisted names. Still prompt (Manual mode) when: an unquoted glob is passed to a command with write/exec-capable flags (`find`, `sort`, `sed`, `git`); `ps` options that print env vars (`ps e`, `ps auxe`); a UNC path argument on Windows; writes to special shell variables (`PATH`, `IFS`); `cd` into another directory combined with `git` (git hooks of that dir could run); `cd` combined with a redirect whose target can't be resolved; the command can't be fully parsed; or it is longer than 10,000 characters.
This list is a versioned data file in `policy/` (not user-configurable; users add ask/deny rules to tighten).

**Decided while building (QUESTIONS Q41):** `cut` and `awk` are read-only (data file `src/policy/shell-parse/read-only.ts`), except an `awk` program containing `system(`, `getline`, `>`, `|` or `ENVIRON`, or `awk -f`.

### 4.7 Sensitive files read by Dovet's own tools

The sandbox credential list (§7.2) only restricts **shell commands**. Dovet's built-in Read, Grep, Glob, `@` mentions and any other internal file reader run outside the sandbox, and reads inside working directories are otherwise auto-approved. So a separate policy covers them:
- **Sensitive-file patterns** (data file in `policy/`, extendable via `permissions.sensitiveFiles`): `**/.env`, `**/.env.*` (except `*.example`, `*.sample`, `*.template`, `*.dist`), `**/*.pem`, `**/*.key`, `**/*.p12`, `**/*.pfx`, `**/id_rsa*`, `**/id_ed25519*`, `**/id_ecdsa*`, `**/.npmrc`, `**/.pypirc`, `**/.netrc`, `**/.git-credentials`, `**/credentials.json`, `**/*service-account*.json`, `**/*.keystore`, `**/.aws/credentials`, `**/.docker/config.json`, `**/secrets.y*ml`, `**/*.tfvars`, `**/terraform.tfstate*`, plus the home-directory credential list of §7.2.
- **Read / Edit / Write of a sensitive file → ask in every mode** except `bypassPermissions`; `dontAsk` → deny. "Don't ask again" saves an explicit `Read(<path>)` allow rule for that exact path only. Users can turn a pattern into an outright deny with a `Read(...)` deny rule.
- **Grep and Glob** skip sensitive files (ripgrep `--glob '!<pattern>'` for each) unless the user passes the file directly as `path` (then the Read rule applies). Results say how many files were skipped.
- **Nothing denied enters the transcript or the log:** the policy decision happens before any read; a denied/unapproved read produces only the error text.
- **Values from workspace `.env*` files** (parsed with a dotenv parser at session start and when they change) join the redaction set (§8), so `cat .env` or a test that prints config in a shell command is redacted too. Honest limit: redaction is a mitigation, not a guarantee.

**Decided while building (QUESTIONS Q36):** `.env.*` is excluded whole, templates included (the safe side); `permissions.sensitiveFiles.add/remove` apply. The home-directory credential list of §7.2 isn't added to Grep/Glob's exclusions: it lies outside the working directories, where reads already ask.

**Decided while building (QUESTIONS Q42):** a sensitive-file ask is lifted only by an allow rule without wildcards naming that path.

### 4.8 Remote actions (built-in ask) [ADR-28]

The sandbox can't tell a read from a publish once a host is allowed (`github.com` approved for cloning also lets `git push` through). Remote actions are therefore recognized from the command and **asked** in `default`, `acceptEdits` and `plan`, **even when sandboxed** (vision non-goal: no autonomous push). The list is data with tests, like the read-only set (§4.6). Recognition uses the analyzer's argv and wrapper stripping, including `git -C <dir> push` and `git -c k=v push`:
- **git:** `push`, `send-email`, `request-pull`.
- **Publishing:** `npm`/`pnpm`/`yarn`/`bun publish`, `cargo publish`, `twine upload`, `gem push`, `dotnet nuget push`, `mvn deploy`, `docker`/`podman push`.
- **gh:**
  - `pr create`/`merge`/`comment`/`review`;
  - `issue create`/`comment`;
  - `release create`;
  - `repo create`/`delete`;
  - `gist create`;
  - `api` with a non-GET method;
  - `workflow run`.
- **Deploy and infrastructure:** `vercel`/`netlify deploy`, `fly deploy`, `wrangler deploy`/`publish`, `terraform`/`tofu apply`/`destroy`, `pulumi up`/`destroy`, `kubectl apply`/`delete`/`patch`, `helm install`/`upgrade`/`uninstall`.
- **Uploads:** `curl` with `-d`/`-F`/`-T`/`--data*`/`--upload-file` or `-X POST|PUT|PATCH|DELETE`; `wget --post-*`; `scp`/`rsync` to a remote target.

Behavior:
- An explicit allow rule naming the command approves it (e.g. `Bash(git push origin feature/*)`). Force-push to the default branch is the exception: only an exact-match rule (no `*`) naming that command approves it (§5).
- In `bypassPermissions` the list doesn't ask (the user chose no prompts); `dontAsk` denies.
- While tainted, these are denied in **every** mode, `bypassPermissions` included (§10).
- **Honest limit:** this is text recognition, a guardrail; the network boundary (§7.4) is what stops unknown destinations.

**Decided while building (QUESTIONS Q42):** the default branch is `main`, `master` and `State.defaultBranch`; a force-push naming no branch, or `HEAD`, counts as the default branch (fail closed). A remote-action ask is lifted only by an allow rule that names the command: no `*`, or two fixed words before it (`git push*`, not `git *`). Every check runs on the command with wrappers (`sudo`, `env`, `timeout`) stripped and the program reduced to its basename.

## 5. Actions no mode auto-approves
Even in `bypassPermissions`: critical-path removals (prompt with countdown), protected-path writes (§4.3), shell commands with network-path arguments (§4.1), `AskUserQuestion`, `ExitPlanMode`, and (v0.2) MCP tools marked `requiresUserInteraction`. Additionally, `git push --force*` (and `--force-with-lease`, `+refspec`) to the default branch is **denied** in every mode unless an exact-match allow rule (no `*`) names that command.

## 6. Permission prompt

Shows the tool, a short description, the exact command/diff/URL, and **why** it's asking in plain words, never a parser's internal names (no matching rule / ask rule `X` / protected path / critical path / outside working directory / unsandboxed retry / taint). Options:

1. **Yes**
2. **Yes, and don't ask again for: `<generated rule>`** — offered only when the prompt can show everything the rule would allow; the rule is the narrowest sensible one (never `Bash(*)`); file edits: "for this session".
3. **No**

**What the user sees is what they approve:**
- Bidirectional-override, zero-width and other invisible or look-alike characters in commands and paths are shown **visibly** (`⟨U+202E⟩`). When any are present, "don't ask again" is withheld, so text can't display as something other than what runs.
- Secret masking in previews never hides commands, paths or destinations: only the secret value is masked.
- If the full command or diff can't be displayed (too long for the screen), it is scrollable, and "don't ask again" is withheld.
- The option text states exactly what the saved rule covers (per-subcommand rules for compound commands, never the raw full command string).
- **Saved rules must round-trip:** a generated rule is tested against the approved call before it's offered. If it wouldn't match it again (multi-line commands, heredocs), or would match more than was shown, only one-time approval is offered.

**Several prompts:** shown one at a time, **oldest first**, with a counter (`2 of 5`); a new prompt never covers the one being read. Clicking the terminal only to focus it never answers a prompt. Enter in a prompt never also submits the input box. Text fields in prompts receive digits and Shift+Tab as text, not as menu shortcuts.

Keys: `Tab` on Yes/No opens a **comment** field. Yes + comment: the comment is delivered to the model after the tool result. No + comment: the comment is the denial reason and the model continues. **No without a comment stops the turn.** `Esc` = No. Some prompts offer only one-time approval (when a saved rule couldn't express exactly what was approved).

Rules can be added/removed live with `/permissions`, **also while a turn runs**; changes apply from the next tool call in the same turn. `/permissions` has a **Recently denied** tab, from which a denial can be turned into a rule.

## 7. Sandbox [DECISION-6]

### 7.1 Implementation
`@anthropic-ai/sandbox-runtime` [VERIFIED 2026-10-11]. Its helper files (Linux `apply-seccomp`, Windows `srt-win.exe`, Java proxy agent) ship in Dovet's `libexec/` directory and are passed by **explicit path** (the library supports explicit paths for each) [DECISION-20].

### 7.2 What it restricts (defaults)
| Access | Default | Settings |
|---|---|---|
| Writes | Working directories + a per-session temp dir (`$TMPDIR` is set to it) | `sandbox.filesystem.allowWrite`, `denyWrite` |
| Reads | Most of the machine **except** the credential deny list | `sandbox.filesystem.denyRead`, `sandbox.credentials` |
| Network | No direct route; all TCP via the local proxy; allowed domains start with the package-registry list (§7.4) | `sandbox.network.allowedDomains`, `deniedDomains` |
| Env vars | Inherited minus `sandbox.credentials.envVars` deny entries and secret-named variables (§8) | `sandbox.credentials` |

**Sandbox protected paths** (write-denied even inside allowed dirs, no exemption): Dovet/Claude config files and dirs (`.dovet/**`, `.claude/**` settings/skills/agents/commands/hooks, `.mcp.json`) in the working dir and its parents; in the working dir: shell startup files, `.gitconfig`, `.vscode`, `.idea`, `.git/hooks`, `.git/config`; files that would turn the working dir into a bare repo (`HEAD`, `objects`, `refs` at top level); Dovet's own config and data dirs.

**v0.2 candidate, credential masking:** sandboxed commands read a *sentinel* copy of a credential, and the sandbox proxy substitutes the real value on the wire, only for allowed hosts. `npm publish` or `aws` can then work without the process ever seeing the secret. It needs TLS interception by the proxy, which is why it isn't in v0.1.

**Default `sandbox.credentials.files` deny list:** `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gcloud`, `~/.azure`, `~/.kube/config`, `~/.docker/config.json`, `~/.netrc`, `~/.npmrc`, `~/.pypirc`, `~/.git-credentials`. Reason: safe by default (principle 2). Users can remove entries in user settings.

### 7.3 Sandbox modes
- **Auto-allow (default, `sandbox.autoAllowBashIfSandboxed: true`):** a shell command that runs inside the sandbox is approved **without a prompt**, even in Manual mode. Still enforced: deny rules; content-scoped ask rules (`Bash(git push *)`); critical-path removals; the read-only exceptions of §4.6 don't matter (sandboxed anyway). A bare `Bash` ask rule is skipped for sandboxed commands. **Not** applied in `plan` mode.
- **Regular permissions mode (`autoAllowBashIfSandboxed: false`):** every shell command goes through §3 even when sandboxed.

### 7.4 Network
- **Violations always reach the model:** the result names each blocked file or host and why, **even when the command exited 0** (e.g. `curl` printing the proxy's 403 page). Hints for common cases: a dev server that can't bind a port → `sandbox.network.allowLocalBinding`; clipboard commands (`pbcopy`, `xclip`) → `/copy`.
- The tool description doesn't list the allowed hosts, so the model tries a request (and the user can approve a new host) instead of assuming unlisted hosts are blocked. It describes the sandbox only as strongly as it's enforced in the current state.
- Domains outside the allowlist: the command waits; **Manual/acceptEdits/plan → prompt** ("Allow `<cmd>` to reach `host`?": Yes for this session / Yes and don't ask again → saves `WebFetch(domain:host)` / No); `dontAsk` → refused; `bypassPermissions` → allowed. `deniedDomains` always refused.
- **Default allowed domains** (package registries only): `registry.npmjs.org`, `registry.yarnpkg.com`, `pypi.org`, `files.pythonhosted.org`, `crates.io`, `static.crates.io`, `index.crates.io`, `proxy.golang.org`, `sum.golang.org`, `rubygems.org`, `repo.maven.apache.org`, `api.nuget.org`. Not `github.com` (broad domains enable exfiltration). Registries are pre-allowed so installs don't prompt. Editable.
- `WebFetch(domain:…)` allow rules also feed the allowlist. `sandbox.network.strictAllowlist: true` (user settings only) refuses instead of prompting.
- Hostnames resolving only to local addresses (loopback, link-local incl. `169.254.169.254`, own interfaces) are refused after resolution; `localhost`/`*.localhost` allowed. Allow a specific local target by IP:port in `allowedDomains`.
- Tools that ignore proxy env vars (plain `ssh`, DB drivers) and non-TCP traffic (UDP, QUIC, ICMP) can't connect; documented in troubleshooting.

**Decided while building (QUESTIONS Q57, Q58):**
- Hosts the sandbox library rejects are dropped from its allow and deny lists (fail closed) and reported through `globWarnings()` as `ambiguous host <h> (see /doctor)`, next to the library's Linux glob warnings; expansion never blocks startup.
- Before a command, `decide` covers the prompt (WebFetch to an unknown host asks; `dontAsk` denies, `bypassPermissions` allows). During a command the proxy asks through `SandboxAskCallback`: denied domains and local literals are denied first; registry, loopback and allowed hosts pass without asking; `strictAllowlist` refuses; `dontAsk` denies; `bypassPermissions` allows; otherwise it waits for the permission prompt (no prompt wired denies).
- Local addresses: IP-literal loopback and link-local (`127/8`, `::1`, `169.254/16`, `fe80::/10` and mapped forms) are denied for WebFetch in `decide`; hostnames that resolve to local addresses are refused by the proxy's resolved-address guard, with no second lookup by Dovet. `localhost` and `*.localhost` are never refused; an exact `IP:port` in `allowedDomains` lifts the refusal.

### 7.5 Escape hatches
- **Unsandboxed retry:** the shell tool has a `dangerouslyDisableSandbox: boolean` parameter. When a command fails in the sandbox, the result names what was blocked (host, path); the model may retry with the flag. The retry runs unsandboxed and **always goes through the normal permission flow** (prompt titled "Shell command (unsandboxed)"; a matching allow rule approves it; `dontAsk` denies). `Bash(dangerouslyDisableSandbox:true)` as an ask rule forces a prompt even in bypass mode.
- **Strict sandbox mode:** `sandbox.allowUnsandboxedCommands: false` ignores the flag. `sandbox.failIfUnavailable: true` refuses to run shell commands when the sandbox can't start.
- **Excluded commands:** `sandbox.excludedCommands: ["docker *", …]` run unsandboxed through the normal permission flow, including a bare `Bash` ask rule. A compound command is excluded only if **every** part matches. Matching uses the same argv rules as permission rules (§3.2): env prefixes, short and long option spellings (`git clone -b` ≡ `--branch`), and quoted `#`/`[WIP]` in messages don't change the result. From project settings, `excludedCommands` applies only in trusted folders and never when `allowUnsandboxedCommands: false`.

**Decided while building (QUESTIONS Q55, Q57):** `allowUnsandboxedCommands: false` ignores both the retry flag and `excludedCommands`, so nothing runs unsandboxed. From an untrusted project file `excludedCommands` is dropped at load (§11), so only user settings, trusted projects and personal local files can exclude a command; the unsandboxed retry still asks (a matching allow rule approves it, `dontAsk` denies). The decision reason names the boundary: `unsandboxed command: … (unsandboxed execution, §7.5)`.

**Decided while building (QUESTIONS Q67):** `dangerouslyDisableSandbox` is a parameter of the `Bash` and `PowerShell` rule matchers, so a rule can name an unsandboxed retry. With `failIfUnavailable`, a command fails when the sandbox is enabled but not healthy. Before every command, `wrap()` re-expands both the session's read-deny and write-deny paths and passes the union to the POSIX and Windows backends.

### 7.5b Sandbox configuration hygiene
- **Path entries are normalized** before use: `~` expanded, trailing slashes removed (a `denyRead: "~/.aws/"` with a slash was silently bypassable), absolute paths accepted without a `//` prefix, and parentheses in paths handled.
- **Globs in sandbox read/write rules** (`~/**/.env`) are expanded within a budget (10,000 entries or 2 s). Beyond it, Dovet warns that the rule can't be fully enforced *inside* the sandbox on Linux, and its own file tools still enforce it. Expansion never blocks startup or bloats tool descriptions.
- **Hosts:** trailing dots stripped in allowed **and** denied lists; IPv6 literals bracketed (`[::1]:443`); ambiguous spellings rejected at load with `/doctor` guidance.
- **Protected entries are anchored:** `.git/hooks` and `.git/config`, never any directory named `hooks/` or `config/`. In a **linked worktree**, writes are allowed to the common git directory's objects, refs and logs but not its `hooks/` and `config`, and never to the main checkout's files.
- **Symlinks among protected paths** (`.dovet/settings.json` managed by stow or home-manager, a symlinked `.dovet/` folder) are denied at both link and target. They are re-checked before each command (late-appearing links). A symlink must never stop the sandbox from starting, and Dovet's cleanup never deletes anything outside its own temp directory.
- **The sandbox leaves no trace in the workspace:** no stub files, mount-point placeholders or lock files (`git status` stays clean, `.git/config.lock` never left behind), and nonexistent paths such as `.git/config.worktree` are not turned into unreadable placeholders. Covered by escape-suite tests.
- **TMPDIR:** sandboxed commands get the session temp directory, created before each command if missing (fresh-boot `mktemp` failures; macOS per-user temp). Unsandboxed commands keep the user's own `TMPDIR` (overriding it breaks bazel and EDR-protected Go builds). The same session never gives one command two different temp directories.
- **No inherited handles:** Dovet opens all its files close-on-exec; sandboxed processes get only stdin/stdout/stderr.
- **Bring-up never blocks the UI:** the sandbox health check runs in the background at startup, and the first shell command waits for it.

An unexpected `getPlatformSupport()` answer counts as unsupported (fail closed).

**Decided while building (QUESTIONS Q87):** the escape suite (`test/platform/mxc/escape-suite.ts`, workflow `windows-escape`) ran against MXC on Windows 11 arm64 and Server 2025 and every escape case held (outside writes by path, `..`, `\\?\`, admin share and planted junction; denied-file reads; egress by name, address and host loopback; host environment secrets). ## 8. Secret handling
- **Child-process env scrub (default on):** variables whose names match `/(KEY|TOKEN|SECRET|PASSWORD|PASSWD|CREDENTIAL|AUTH)/i` are removed from shell tool environments unless listed in `shell.passEnv`. Reason: safe by default (principle 2).
- **Output redaction:** values of those variables, and known key formats (`sk-ant-`, `sk-`, `sk-or-`, `AIza`, `ghp_/gho_/ghu_/ghs_/github_pat_`, `glpat-`, `xox[abpr]-`, `AKIA/ASIA`, PEM private keys, JWTs), are replaced with `[REDACTED:<name>]` in tool results before they reach the model or the log. Not a security boundary; documented as such.
  The redaction test corpus (`policy/testdata/redaction-corpus.jsonl`) includes the known miss cases: a key name with no value, JSON inside a shell string, zero-width characters inside key names, URL passwords containing `)`, quotes, `]`, `&`, a second `@` or `%40`.
- Credential **masking** via the proxy (TLS termination + sentinel substitution) is v0.2.

**Decided while building (QUESTIONS Q60, Q69):**
- Redaction labels: a value is replaced by `[REDACTED:<variable name>]`; key formats use a fixed kind (`ANTHROPIC_KEY`, `OPENROUTER_KEY`, `OPENAI_KEY`, `GOOGLE_API_KEY`, `GITHUB_TOKEN`, `GITLAB_TOKEN`, `SLACK_TOKEN`, `AWS_ACCESS_KEY_ID`, `PRIVATE_KEY`, `JWT`); a URL password is `URL_PASSWORD`. Values under 8 characters never redact by value.
- Tool results carry `[REDACTED:<name>]` into both the model and the log from the loop boundary; the log writer keeps `[redacted]` as the backstop for other fields.
- `.env` scan: `.env` and `.env.*` under the working directories, except `*.example`, `*.sample`, `*.template` and `*.dist`, skipping `node_modules`, `.git` and `target`-style trees. Built at session start and re-read for a tool result when a file's mtime changed; a new nested file is picked up when a working directory's root mtime changes.

**Decided while building (QUESTIONS Q69):** in `.env` parsing, an unquoted value ends at an inline comment (`\s+#`, or `#` at the start), and a quoted value may span several lines. Redaction maps positions in UTF-16 code units, so a secret after an emoji or another astral character is cut exactly.

## 9. Auto mode [v0.2]
Specified now so v0.1 doesn't block it:
- **Placement [ADR-28]:** the reviewer sees only actions that **already** need approval under §0b (boundary crossings), never in-boundary actions. It replaces the human for those prompts, not the sandbox. This keeps reviewer cost, latency and injection surface small, and works with any provider's model.
- Decision order per action: (1) rules resolve (with the §4 exceptions: protected paths, critical paths, network paths, content ask rules still apply); (2) in-boundary actions run (§0b); (3) boundary crossings → **reviewer**; (4) a block returns the reason to the model; critical-path removals and protected-path writes still go to the user.
- Classifier input: user messages, tool calls (not tool **results** — prompt-injection resistance), project instructions; output: allow/block with a rule name. Default blocked categories: download-and-execute, exfiltration, force push, discarding uncommitted work, infrastructure destroy, secrets in commits, …
- Model: configurable (`autoMode.model`, default the provider's cheapest capable model); each call is a visible, counted `model.request` (principle 3).
- On entering auto mode, broad allow rules granting arbitrary execution (`Bash(*)`, `Bash(python*)`, package-manager run rules) are suspended; restored on exit.
- Fallback: 3 consecutive or 20 total blocks → back to prompting.
- Boundaries stated by the user ("don't push") are read from the transcript by the classifier.

## 10. Taint and prompt-injection defense

**Design frame: the "lethal trifecta" / Agents Rule of Two.** An agent that combines (A) untrusted input, (B) access to private data and (C) the ability to change state or communicate externally can be steered by injected text into leaking data (Willison's "lethal trifecta"; Meta's "Agents Rule of Two", Nov 2025). Until injection can be reliably detected, a session should hold at most two legs autonomously; with all three, a human supervises. A coding agent always reads untrusted repository content (A), so Dovet removes or limits the other legs by default, and **taint** cuts them further when stronger untrusted input arrives:

| Leg | Default (untainted) | While tainted |
|---|---|---|
| (B) private data | Credential files denied to sandboxed commands (§7.2); sensitive files ask (§4.7); secret env vars scrubbed (§8) | Sensitive-file reads still ask, but with a red `session tainted by <source>` banner and **no** "don't ask again" |
| (C) external communication | Sandbox network limited to package registries; new hosts ask (§7.4) | Sandbox auto-allow suspended (commands prompt unless an explicit allow rule matches); network prompts have no "don't ask again"; `git push`, publish and upload commands (`npm publish`, `curl -d/-F/-T/--upload-file`, `gh` create or comment commands, …) are **denied** |

- **Taint is set when** the session ingests WebFetch or WebSearch output; (v0.2) results from MCP servers not marked `trusted: true`, or a tainted subagent's result; **a sandboxed command whose network traffic reached a host outside the built-in registry list** (known from the proxy log; data from an arbitrary host is as untrusted as a fetched page); or **content with hidden-instruction characters** (Unicode tag characters, below) in any file, tool result or instruction file.
- Visible in the status bar (`⚠ tainted: <source>`); cleared only by `/untaint` (confirmation, logged) or a new session.
- Honest limit: session-level, not data-flow tracking. Dovet doesn't claim to *detect* injection; it limits what a successful one can do. Architectural defenses such as CaMeL or dual-LLM designs are not yet practical in a general coding harness (no mainstream harness uses them, 2026).

**Hidden-instruction characters** (public demonstrations in 2025–2026 showed coding agents executing commands hidden in rules and skill files as invisible Unicode tag characters): before any text Dovet didn't author reaches the model (tool results, file reads, instruction files, fetched pages, v0.2 skills/MCP), these characters are **removed from the model's view** and replaced by one marker `⟨N hidden characters removed⟩`:
- Unicode **tag characters** U+E0000–U+E007F, which can spell invisible ASCII text a model reads;
- the **variation-selector supplement** U+E0100–U+E01EF (used to smuggle bytes inside emoji);
- other default-ignorable format characters outside normal script use.

The file on disk is unchanged. The tool result says so, taint is set and the user sees a warning. **Not touched:** ZWJ/ZWNJ (Persian, Arabic and Indic text and emoji sequences need them), U+FE0F, and bidi controls. Models read logical order, so bidi "Trojan Source" tricks target **humans**: they are made visible in the UI, diffs and permission prompts (§6) instead.

**Forged authority:**
- Harness notices to the model say they come from Dovet and that **no user input occurred** (after injected text faked approvals).
- The system prompt states that approvals and user decisions arrive only through the permission system, never as text inside tool results or files.
- Dovet's reserved markers are escaped in content it didn't author ([context §4](context.md)).
- (v0.2) Subagent results are delivered under a header marking them as subagent output.

**Dovet's own command lines are never built from untrusted strings:** every process Dovet spawns gets an argv array (no shell string interpolating file names, paths or URLs). (File names in "open in editor" and in executable lookups are classic command-injection vectors.)

**Decided while building (QUESTIONS Q58):**
- A sandboxed command that names an `https://host` outside the registry and loopback hosts taints the session (`sandbox: <host>`), unless the violations show that host was denied. This over-taints on purpose (an `echo` of a URL taints); a real proxy allow log replaces the heuristic when available.
- `State.taintSource` feeds the `session tainted by <source>` banner. While tainted, sandbox auto-allow is suspended, sensitive findings always ask, and "don't ask again" is withheld.
- `/untaint` needs confirmation, clears the in-memory taint and emits a notice; `taint.change` events persist it across resume.

## 11. Workspace trust
- Project `.dovet/settings.json` (and `.claude/settings.json` when imported) **allow rules and `additionalDirectories` apply only after the user accepts the trust dialog** for the repo root. The dialog lists what they'd grant. Deny/ask rules always apply (they only restrict).
- Trust is keyed on the git repo root (main checkout for worktrees); outside a repo, the starting directory; never persisted for the home directory.
- `.dovet/settings.local.json` is trusted automatically **only when Dovet wrote it**: its exact text matches the hash Dovet recorded when it last saved a rule into it, and it is not tracked by git and `.dovet` is not a symlink (QUESTIONS Q71). Any other local file is treated as repo-supplied.
- Headless (`-p`) never shows the dialog: untrusted project allow rules are ignored with a stderr warning.

**Decided while building (QUESTIONS Q70):**
- **What an untrusted repo-supplied file still contributes** (an allowlist in `src/store/config/trust.ts`, so a key added later stays ignored until classified). The merge lets a higher layer replace scalars and non-rule arrays, so an untrusted file may keep only what no value in it can turn into less than the user chose: `deny` and `ask` rules (rule lists add up, they never replace), `disableBypassPermissionsMode`, `blockReadsOutsideWorkingDirectories: true`, sandbox booleans that only tighten (`enabled: true`, `failIfUnavailable: true`, `allowUnsandboxedCommands: false`, `autoAllowBashIfSandboxed: false`, `network.strictAllowlist: true`), and `ui`. Everything else is ignored until the folder is trusted, including `model`, `effort`, `compaction`, `cache`, `instructions`, `read`, `webfetch`, `git` (they would replace the user's cost controls), `defaultMode`, `provider`, every other list (`sensitiveFiles.add`, `filesystem.denyRead`/`denyWrite`, `network.deniedDomains`, `credentials`, `examples`: a repo's empty list would wipe the user's own), `compat`, `glob`, `env`, `shell`, `providers`, `network`, `plan`, `budget`, `retention`, `models`, and the other `sandbox` keys. A repo that wants to restrict a path uses a `Read(...)`/`Edit(...)` deny rule.
- The same filter applies to `.claude/settings.json` and, when the repo supplies them, to the two local files. The loader warns once per file: `this folder isn't trusted, so N allow rules and these settings are ignored: …`; headless prints it on stderr, and `LoadedSettings.untrusted` carries the same data for the trust dialog (M3-10).
- A decision is stored in `<data>/trusted-folders.json` as `{ hash, trusted }` per repo root, keyed by the case-folded path on Windows and macOS. The hash is SHA-256 over the repo-supplied files' names and text (`.dovet/settings.json`, `.claude/settings.json`, and the two local files only when the repo supplies them), so any edit asks again. A recorded refusal and the home directory are never trusted.
- **Repo-supplied local files:** `.dovet` or `.claude` is a symlink or a submodule (or has its own `.git`), git tracks `settings.local.json` in either (matched ignoring case, as a case-insensitive volume would open it), git can't answer (not installed, other error), or the folder has no `.git` at all (an unpacked archive can ship the file, and nothing tells it from a personal one). A trusted folder trusts its local files too.
- **A local file counts as Dovet's own only when Dovet wrote it (QUESTIONS Q71):** "not tracked by git" proves nothing (a gitignored file in an archive of a real checkout, or an archive with a minimal `.git`, passes it). `saveLocalRule` records the SHA-256 of the exact text it wrote, per project root (case-folded on Windows and macOS), in `<data>/local-settings.json`. At startup and on reload, `.dovet/settings.local.json` is personal only if its text matches that record and the structural checks above pass; a file written by hand, edited since, copied to another folder, or recorded in a missing or damaged `local-settings.json` is repo-supplied, so its rules wait for the trust dialog and its text joins the trust hash. `.claude/settings.local.json` is never personal, since Dovet never writes it. A project with no local file has nothing to distrust. `saveLocalRule` records the file only when it did not exist before the save or already matched the record, so saving one rule never blesses a file the repo supplied. The cost: a user who edits `.dovet/settings.local.json` by hand (or whose file came from the repo) has it ignored, headless warns on stderr, until they trust the folder; a rule saved into such a file is written but the file stays repo-supplied.
- **Live reload asks again:** a reload re-resolves trust (file origin and config hash) instead of reusing the startup decision, so a `git pull` or checkout that changes a project file mid-session is judged as untrusted until the folder is trusted again. Warnings that quote a settings key are printed with control characters escaped (`\u{1b}`).

## 12. Hooks interplay [v0.2]
`PreToolUse` hooks run before the permission decision and can deny, ask, or allow; **deny and ask rules are evaluated regardless of a hook's "allow"**. A hook exiting with code 2 blocks the call before rules. No hook can approve a critical-path removal.
