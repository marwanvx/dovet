[DECISION-19] Two snapshot mechanisms behind one interface, chosen per workspace:

| Workspace | Mechanism | Covers |
|---|---|---|
| Git repository (and `git` ≥ 2.20 installed) | **Git tree snapshots in a private object store** (below) | Dovet file tools **and shell commands** (sandbox auto-allow makes shell edits common, so they must be undoable) |
| Not a git repo, or no `git` | **File-level blobs** (before-content of each file Dovet's tools modify, in the blob store) | Dovet file tools only; shell changes reported as not restorable |

Why git snapshots: with sandbox auto-allow ([permissions §7.3](permissions.md)), shell commands modify files without prompts, so "file tools only" checkpoints would leave most changes unrecoverable. A separate shadow repository would duplicate the whole project; the design below reuses the repo's existing objects instead.

## Git tree snapshots

- **Private index and stat cache, one per session:** `GIT_INDEX_FILE=<data>/projects/<id>/sessions/<session>.snap.index` and `<session>.snap.stat` (Dovet's own `path → size, mtimeNs, inode, blobId` cache). At session start the stat cache is **copied** from the project's most recent session, so the first snapshot only hashes files changed since then. Per-session files mean two Dovet sessions in one project never share mutable state. The object store is shared: git object writes are content-addressed and atomic, so concurrent sessions are safe.
- **Submodules and nested repos:** snapshots cover the top-level repository; submodule contents are recorded as gitlinks (not restorable), and the receipt says so. A nested repo that is not a submodule is treated as untracked content of the parent (its `.git` excluded).
- **Worktrees:** in a linked worktree, `<repo>/.git` is a file. Dovet runs git from the top level (`git rev-parse --show-toplevel`); because the private object store is self-contained, nothing else from the main repository is needed.
- **Private object store:** `GIT_OBJECT_DIRECTORY=<data>/projects/<id>/objects`, **with no alternate**. Every blob and tree a checkpoint needs is written there, so the store is self-contained. **Nothing is written into the user's `.git`**: no refs, no objects, no index changes, and not even a timestamp (when an existing object is found through an alternate, git refreshes its modification time to protect it from pruning, which would modify the user's repository), and a checkpoint stays restorable after the user prunes, garbage-collects or rewrites their own history. The cost is that the first snapshot stores a compressed copy of every file in the workspace (about 13% of the source size in the 100,000-file benchmark of M0); later snapshots add only changed files.
- **Snapshot (filter-free):** `git add` is **never** used. It runs attribute-selected clean/process filters (`filter.<driver>.clean` / `.process`), plus `ident`, `text`/`eol` and `working-tree-encoding` conversion, on every added file [VERIFIED, git-scm.com/docs/gitattributes]. A repository could make Dovet execute a configured program just by being snapshotted. Instead:
  1. List paths with `git -c core.fsmonitor=false ls-files -z --cached --stage` (the stage output gives each submodule's commit id) and `ls-files -z --others --exclude-standard`, run against the **user's real index read-only** (`GIT_OPTIONAL_LOCKS=0`, no `GIT_INDEX_FILE` override for this step). No filters run; `.gitignore` is respected; tracked-but-deleted files simply don't exist on disk and are omitted. A nested repository shows up as a directory entry; its files are listed by running `ls-files --cached --others --exclude-standard` inside it (its own ignore rules apply, its `.git` is never listed) and count as untracked content of the parent. A path containing a newline is not supported (`--stdin-paths` is newline-separated): it is left out and listed in the receipt.
  2. For each path, compare `(size, mtimeNs, inode)` with Dovet's own per-session stat cache (`<session>.snap.stat`); only changed files are hashed. A file modified less than 2 s before the snapshot started is not cached, because timestamps can be coarse and the file could change again without its modification time moving.
  3. Store changed files' **raw bytes** as blobs in the private object store with **one `git fast-import` process** that Dovet streams exact-length `blob` records into (`data <byte count>`, never delimiter-based, so file content can never be mistaken for a command; fast-import runs no filters). The blob ids come back through `--export-marks`. A symlink is stored as a link (mode 120000) whose blob is its target text, never followed. One pack instead of one loose object file per blob matters on Windows: creating a loose object cost about 8 ms on a CI runner's C: drive (80 times the pack's cost), which made a first snapshot of 100,000 files take 13 minutes. `fast-import` runs inside an empty bare repository of Dovet's own (`<data>/projects/<id>/git`) with `GIT_OBJECT_DIRECTORY` pointing at the private store, because on a fatal error it writes a crash report into the top level of the repository it runs in, and that must never be the user's `.git`.
  4. Rebuild the private index from scratch each time (`git read-tree --empty`, then the full list via `git update-index -z --index-info`: mode, blob id, path; object ids only, no filters; unchanged files reuse blob ids from the stat cache, so this is cheap), then `git write-tree`. Rebuilding avoids any stale-entry or deletion bookkeeping.
  5. All git invocations get `-c core.fsmonitor=false -c core.hooksPath=<empty dir>`, `GIT_OPTIONAL_LOCKS=0`, and a scrubbed environment; no other git subcommand is used.
  **Restore** likewise never uses `checkout-index` or `checkout` (they run smudge filters): blob bytes are read with `git cat-file --batch` and written by Dovet with the normal atomic write. The tree id passed to restore must be a full object id. Because snapshots store raw working-tree bytes, a restore reproduces exactly what was on disk.
- **When:** before the first mutation in each user turn (`checkpoint` event `c<turn>`, recording the tree id), and before/after each non-read-only shell command (to attribute changes to that command in the receipt). The checkpoint is taken lazily: a turn that changes nothing logs none. A shell command's own before-snapshot is the turn's checkpoint when it comes first; a file tool awaits the snapshot before it writes. Where the workspace has no git ≥ 2.20 (or `checkpoints.enabled` is false) the same event is logged per file Dovet's own tools change, once per path per turn, with `mechanism: "blobs"` and the old bytes' blob-store hash (`null` for a new file); a rewind restores the earliest saved state of each path from that turn on. The first shell command of a turn that has no snapshots says why in its result: shell changes can't be undone, Edit and Write changes can (QUESTIONS Q79).
- **Diff:** `git diff-tree -r --name-status <before> <after>` gives the exact changed paths for `file.change` events.
- **Restore never writes through links:** a tracked path that is now a symlink or a hard-linked file is skipped and counted (`Skipped N paths that are links now.`). So is a path with a symlink at any directory above it, in git and blob mode alike (blob mode checks from the workspace down, and for a path outside the workspace from the drive root, so a link anywhere in that path skips it) (QUESTIONS Q105).
- **Restore:** for the chosen checkpoint tree, compute the paths that differ from the current state (`git diff-tree -r -z <checkpoint> <current snapshot>`), write each one's bytes from `git cat-file --batch` with Dovet's atomic write (**never** `checkout-index`/`checkout`, see above), and delete files created after the checkpoint (and the directories that leaves empty). A path that existed at the checkpoint but was left out of it (over the size limits, for example) is never deleted: the snapshot returns its list of left-out paths and restore takes it back. Existing files keep their permissions; only the execute bit follows the checkpoint. Never touch ignored files or `.git/`.
- **GC:** `dovet gc` removes snapshot objects not referenced by any checkpoint within the retention period (`git prune` on the private store with a temporary ref list) (QUESTIONS Q81): the roots are the trees of every non-expired session's `checkpoint` events and the blobs in the stat caches that remain (an expired session's `.snap.stat` and `.snap.index` are deleted, they are only caches); they become refs of a throwaway bare repository sharing the private object store, then `git repack -A -d --unpack-unreachable=<grace>` drops unreachable packed objects and `git prune --expire=<grace>` unreachable loose ones (grace: one hour). A project with a running session is left alone.

- **Size limits:** **untracked** (new, not ignored) files over **2 MiB** and **any** file over 50 MB are excluded from snapshots and listed in the receipt as not restorable. Logs, datasets and binaries the agent creates would otherwise bloat the store. Dovet's own file tools still record their before-content in the blob store, so an Edit/Write of a large file stays restorable.
- **The private store never garbage-collects on its own:** every git call on it runs with `-c gc.auto=0 -c maintenance.auto=false`. Only `dovet gc` prunes, and only objects no retained checkpoint references (git's background gc would otherwise delete undo points).
- **Turning snapshots off:** `checkpoints.enabled: false` (per project, for huge repositories) keeps only the file-level blobs for Dovet's own tool edits. Already-stored snapshots stay until `dovet gc` or `dovet project purge`.

## File-level blobs (fallback)

Before Edit/Write modifies a file, its prior content goes to the blob store, once per path per turn. Rewind restores from blobs.

## Rewind

`/rewind` (alias `/undo`; or Esc Esc on an empty prompt) opens a picker listing **every** user message, including ones sent while the agent was working. Each entry shows a one-line preview (long pastes and file contents truncated, so the picker stays fast; image-only messages show `[image]`) and the turn's receipt summary: files changed, and whether they can be restored. Choosing turn *k*:

| Option | Effect |
|---|---|
| **Restore files to before turn k** | Restore every path changed in turns ≥ k to its state at checkpoint `c<k>`. Append an instruction: `The user restored files to their state before turn k. Re-read files before editing them.` Clear read-state for restored paths. |
| **Fork conversation at turn k** | New session (`session.fork`) whose log copies events before turn *k*'s user message; that message goes back into the input box. The original session is untouched. Files unchanged. |
| **Both** | Restore files, then fork. |
| **Summarize up to here** | Keep turns ≥ *k* as they are and replace everything before turn *k* with a summary, i.e. a compaction ([context §6](context.md)) that starts a new epoch whose history is the summary followed by turns ≥ *k*. Files unchanged. Kept assistant turns are carried as in a model switch: provider-opaque reasoning is dropped, because it was bound to the old prefix. Use it to free context without losing recent detail. |

**After a fork,** `dovet --continue` and `/resume`'s default point at the **fork** (the newest session); the original stays listed. A prompt sent right after rewinding belongs to the fork and is never lost, even if Dovet is killed before the next turn ends. The fork's log is the parent's lines before turn *k*'s user message, copied as they are and followed by a `session.fork` event naming the parent and its last copied event (the checkpoint and `file.change` events come along, and they name the project's snapshot objects and the blob store, which every session of the project shares); the new session is the project's newest, so `--continue` finds it by its id, and the fork is fsynced before the input box gets the message back. A `user.message` is flushed and fsynced the moment it is logged, so a prompt typed right after a rewind is already in the fork's file when the model call starts (QUESTIONS Q80). A fork **references** the parent's snapshot and blob data rather than copying it, and GC treats every session referencing an object as a reference. A forked session can therefore never restore a truncated or zero-filled file.

**Restores are verified, never assumed:** each restored file is re-hashed after writing. The result lists restored, skipped (conflict, link, expired) and failed paths with counts. If any needed snapshot or blob is missing, the rewind says exactly which paths couldn't be restored, and never reports success.

**Conflict safety:** before restoring, compare each path's current content with the last state Dovet recorded: the `after` hash (SHA-256 of the bytes it left, `null` = deleted) of the path's latest `file.change`, which Edit, Write and every path a shell command changed record (a command that changes more than 20 files records the first 20). A path whose bytes differ from that, or that has no record at all, is a conflict; a path that isn't on disk never is, and neither is one whose bytes already equal the restored ones (QUESTIONS Q80). Paths changed since (by the user or outside Dovet) are listed: "Overwrite them anyway? [Overwrite] [Skip these] [Cancel]". Never overwrite silently.

Restores use the Write strategy of [tools §2.7](tools.md) (atomic rename, or in-place for bind-mounted and other identity-sensitive files; tracked paths that became links are skipped) and are recorded as `file.change` with `via: "rewind"`, so a rewind is itself rewindable: each carries `after` and a `before` (the blob-store hash of the bytes it replaced, which the rewind keeps there).

## Limits (stated to the user)

- Changes outside the workspace (global installs, other directories, databases, network side effects) are never restorable.
- If a snapshot exceeds 2 s (huge repos), shell snapshots are disabled for the session with a visible notice; Dovet tool edits fall back to file-level blobs. The limit applies to every snapshot's time outside storing new file content (the first snapshot of a repository stores every file and is not judged by that); the snapshot that went over still is the turn's checkpoint, later turns use blobs (QUESTIONS Q79).

## Acceptance criteria

- [ ] **AC-CKPT-01** Git workspace: a shell command `sed -i` + `rm` + creating a new file; rewinding restores both files and deletes the new one.
- [ ] **AC-CKPT-02** After snapshotting, `git status`, `.git/index`, refs and `.git/objects` of the user's repo are byte-identical to before.
- [ ] **AC-CKPT-03** **Filter safety:** a repo whose `.gitattributes` selects a clean filter and a process filter (configured in local and global config) that write a marker file and attempt a network call: snapshot and restore never create the marker or connect.
- [ ] **AC-CKPT-04** Files with `text=auto`/`eol=crlf`/`ident`/`working-tree-encoding` attributes round-trip byte-identically through snapshot + restore.
- [ ] **AC-CKPT-05** Second snapshot of an unchanged 10k-file repo completes in < 200 ms on Linux and macOS and < 400 ms on Windows (stat cache works; QUESTIONS Q72).
- [ ] **AC-CKPT-06** Non-git workspace: Edit + Write rewind via blobs; a shell change is reported as not restorable.
- [ ] **AC-CKPT-07** Conflict prompt appears when a file changed after Dovet's last write.
- [ ] **AC-CKPT-08** Fork leaves the original session log byte-identical.
- [ ] **AC-CKPT-09** Windows: snapshots and restores work with CRLF files and paths with spaces.
- [ ] **AC-CKPT-10** A new 5 MB untracked log and a 60 MB tracked file are excluded and reported as not restorable; an Edit of a 3 MB file is still restorable via blobs; `git count-objects` on the private store after 100 snapshots shows no automatic gc ran; `dovet gc` keeps every object referenced by a retained checkpoint.
- [ ] **AC-CKPT-11** Rewind with one snapshot blob deleted: the result names the unrestorable path and doesn't report success; restored files' hashes match the checkpoint.
- [ ] **AC-CKPT-12** A fork restores the same files as its parent; deleting the parent session doesn't break the fork's rewind; `--continue` after a fork opens the fork; a prompt sent right after `/rewind` survives a SIGKILL.
- [ ] **AC-CKPT-13** "Summarize up to here" at turn 5 of 9: the next request contains the summary plus turns 5–9 verbatim (without reasoning blocks) and succeeds on Anthropic with `prefix_mismatch_behavior: "error"`.
